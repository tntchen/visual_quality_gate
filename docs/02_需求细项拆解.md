# 前端体验质量门禁：需求细项拆解

## 1. 拆解原则

1. 每项需求必须能回答“检查谁、何时检查、如何判定、失败后怎么办”。
2. 确定性规则与 AI 概率性判断分开验收。
3. 提测门禁与发布门禁分开定义。
4. 阈值不直接拍脑袋统一，先通过现状采样和历史缺陷确定。
5. 本文中的 P0/P1/P2 表示需求建设优先级，不等同于缺陷或门禁阻断级别。

## 2. 角色及核心使用场景

| 角色 | 核心诉求 | 典型使用场景 |
|---|---|---|
| 研发人员 | 提测前快速发现问题，失败原因清楚 | 提交代码或部署后执行走查，按报告修复并复检 |
| 测试人员 | 低级问题不流入测试，门禁结果可信 | 制定规则、抽检结果、处理漏报和误报 |
| 设计人员 | UI 判断有依据，容差合理 | 确认设计基线、关键区域和可接受差异 |
| 前端/应用负责人 | 脚本和规则维护成本可控 | 管理应用接入、页面变更和责任人 |
| 架构/平台人员 | 多应用可复用，不和单一工具强绑定 | 管理执行器、规则模型、流水线和产物接口 |
| 发布管理人员 | 阻断有依据，紧急发布可审计 | 查看门禁结果、审批豁免、追踪例外 |
| 需求/管理人员 | 能证明质量收益 | 查看拦截缺陷、巡检成本和趋势 |

## 3. 场景与资产类需求

| 编号 | 需求细项 | 验收口径 | 优先级 |
|---|---|---|---|
| AST-01 | 建立应用、页面、路由、负责人和重要等级清单 | 试点范围内对象均有唯一标识和责任人 | P0 |
| AST-02 | 建立核心链路清单，明确入口、步骤、预期结果和涉及接口 | 每条链路可由研发、测试共同确认 | P0 |
| AST-03 | 管理测试账号、角色、测试数据和前置状态 | 同一链路可按约定数据重复执行 | P0 |
| AST-04 | 管理浏览器、分辨率、终端及操作系统覆盖矩阵 | 每类页面有明确覆盖范围，不默认全量覆盖 | P1 |
| AST-05 | 建立页面与设计稿、组件规范、截图基线的对应关系 | 基线有版本、生效时间和确认人 | P1 |
| AST-06 | 记录后端依赖、第三方依赖及可用性要求 | 环境异常能与产品缺陷区分 | P0 |

## 4. 指标与规则类需求

### 4.1 核心交互与前端异常

| 编号 | 需求细项 | 判定及证据 | 优先级 |
|---|---|---|---|
| INT-01 | 页面可访问，无空白页、明显加载失败或异常跳转 | 保存最终页面、访问地址、截图及控制台信息 | P0 |
| INT-02 | 核心链路可按预期步骤执行并达到业务结果 | 每步有状态，失败时保留截图、录像或轨迹 | P0 |
| INT-03 | 核心按钮、链接、表单及弹窗可用 | 校验可操作状态及操作结果，不仅检查元素存在 | P0 |
| INT-04 | 加载中、空数据、业务失败、系统异常等状态有合理反馈 | 按场景构造或 mock，验证页面反馈 | P1 |
| INT-05 | 防止重复提交、重复点击导致异常业务结果 | 结合接口调用次数及页面反馈判断 | P1 |
| INT-06 | 采集未捕获脚本异常、Console Error、资源加载失败 | 支持白名单，白名单需有原因和有效期 | P0 |
| INT-07 | 检查死链、关键图片破损及明显文字溢出 | 先覆盖关键页面和关键区域 | P1 |

### 4.2 接口稳定性与契约

| 编号 | 需求细项 | 判定及证据 | 优先级 |
|---|---|---|---|
| API-01 | 同时判断 HTTP 状态和业务返回码 | 业务成功规则由接口责任方确认 | P0 |
| API-02 | 校验核心接口响应结构、关键字段和必要枚举值 | 兼容约定的契约版本，记录实际差异 | P0 |
| API-03 | 统计核心接口响应时间、超时和失败情况 | 建议按 P95 等口径评估，采样方式需统一 | P0 |
| API-04 | 识别页面成功提示与实际接口失败不一致 | 关联页面步骤、接口请求和页面结果 | P1 |
| API-05 | 区分接口自身缺陷、环境不可用、测试数据问题和第三方异常 | 失败分类可进入不同处理流程 | P0 |
| API-06 | 对敏感字段脱敏，控制报文及截图访问权限 | 报告不暴露超出授权范围的数据 | P0 |

### 4.3 页面性能

| 编号 | 需求细项 | 判定及证据 | 优先级 |
|---|---|---|---|
| PERF-01 | 采集首屏及核心 Web 性能指标 | 明确指标定义、页面采样点和采集工具口径 | P0 |
| PERF-02 | 支持按页面等级、网络条件和终端类型设置阈值 | 不同场景可配置，不使用单一全局阈值 | P1 |
| PERF-03 | 支持固定环境、多次采样和异常值处理 | 重复执行结果具备可解释性 | P0 |
| PERF-04 | 识别明显性能退化 | 与基线或上一稳定版本比较，并保留原始数据 | P1 |
| PERF-05 | 区分实验室性能与生产真实用户性能 | 报告明确数据来源，二者不混用 | P1 |

### 4.4 UI 还原度与视觉基线

| 编号 | 需求细项 | 判定及证据 | 优先级 |
|---|---|---|---|
| UI-01 | 对关键页面或组件建立经设计确认的截图基线 | 基线关联页面版本、视口、数据和设计版本 | P1 |
| UI-02 | 支持动态时间、随机内容、广告位等区域遮罩 | 非业务变化不重复形成无效差异 | P1 |
| UI-03 | 支持关键区域和全页面不同容差 | 核心区域可采用更严格规则 | P1 |
| UI-04 | 输出原图、现状图、差异图和差异位置 | 设计或研发可直接判断差异性质 | P1 |
| UI-05 | 页面改版后支持基线审核和更新 | 不允许执行工具自动覆盖旧基线 | P1 |
| UI-06 | AI 可辅助识别不美观、文案重叠等疑似问题 | 作为人工评审输入，不直接替代设计验收 | P2 |

## 5. 执行与门禁类需求

| 编号 | 需求细项 | 验收口径 | 优先级 |
|---|---|---|---|
| EXE-01 | 支持研发手动触发及部署后自动触发 | 两种方式使用同一规则和结果模型 | P0 |
| EXE-02 | 执行前检查环境、账号、依赖和基础页面可用性 | 环境不满足时明确终止，不判为产品缺陷 | P0 |
| EXE-03 | 支持超时、重试、取消和并发限制 | 重试次数及执行时长可配置、可追踪 | P0 |
| EXE-04 | 统一记录通过、产品失败、脚本失败、环境失败、平台失败 | 各状态有明确处理责任和统计口径 | P0 |
| GATE-01 | 支持阻断、警告、观察三类门禁结果 | 每类规则可独立配置 | P0 |
| GATE-02 | 支持提测门禁和发布门禁 | 两个节点可配置不同范围和严格程度 | P0 |
| GATE-03 | 阻断规则仅使用明确、稳定、可复现的判定 | AI 疑似问题不得默认成为 P0 阻断依据 | P0 |
| GATE-04 | 支持有审批人、原因、范围和有效期的豁免 | 过期自动失效，保留完整审计记录 | P0 |
| GATE-05 | 支持告警期转阻断期 | 可查看告警期误报和稳定性数据 | P0 |
| GATE-06 | 规则、阈值、脚本和基线均关联版本 | 可解释某次结果使用的是哪套标准 | P1 |

## 6. 报告与闭环类需求

| 编号 | 需求细项 | 验收口径 | 优先级 |
|---|---|---|---|
| RPT-01 | 输出应用、代码版本、环境、时间、规则版本及总体结果 | 任一结果均可追溯到具体执行上下文 | P0 |
| RPT-02 | 失败结果提供步骤、截图、接口或控制台证据 | 研发无需重新完整走查即可开始定位 | P0 |
| RPT-03 | 支持失败后的单规则或单链路复检 | 不必每次全量执行 | P1 |
| RPT-04 | 支持转为缺陷或关联已有缺陷 | 避免同一问题重复派单 | P1 |
| RPT-05 | 统计拦截、漏报、误报、豁免、执行时长和人工耗时 | 能用于评价质量收益及运行成本 | P1 |
| RPT-06 | 配置报告、截图、录像和报文保留期限 | 满足审计同时控制存储成本 | P1 |

## 7. AI 辅助走查需求

| 编号 | 需求细项 | 验收口径 | 优先级 |
|---|---|---|---|
| AI-01 | 根据页面结构、需求和核心链路推荐走查范围 | 推荐结果可查看来源，可由测试人员调整 | P1 |
| AI-02 | 探索固定脚本未覆盖的页面、操作和异常路径 | 记录实际操作路径，不仅给文字结论 | P2 |
| AI-03 | 输出疑似问题、证据、复现步骤和置信说明 | 无证据的判断不得直接生成正式缺陷 | P1 |
| AI-04 | 支持人工确认、误报标记和结果归类 | 反馈可用于调整后续走查策略 | P1 |
| AI-05 | 将重复出现且确认有效的问题转为确定性规则候选 | 新规则须经评审后进入硬门禁 | P1 |
| AI-06 | 辅助生成或修复脚本时保留人工审核环节 | 未经审核的脚本不得直接控制发布 | P1 |
| AI-07 | 明确模型部署、输入输出、敏感数据及调用成本边界 | 满足企业安全和成本要求 | P0（前置调查） |

## 8. 非功能需求

### 8.1 稳定性与可重复性

- 同一版本、同一环境、同一数据条件下，结果应具有可解释的一致性。
- 自动重试不能掩盖真实缺陷，首次和重试结果均需保留。
- 平台自身失败不得被统计为产品质量失败。

### 8.2 可维护性

- 页面定位、流程步骤、判定规则和环境配置尽量分离。
- 公共组件和通用检查规则可复用，业务链路允许单独维护。
- 基线更新、规则变更和白名单均需要记录。

### 8.3 性能与容量

- 明确单链路、单页面和全量门禁的执行时长目标。
- 支持按变更范围执行部分检查，避免所有提交都全量走查。
- 明确并发数、排队策略和产物保留策略。

### 8.4 安全与权限

- 测试账号最小权限，凭据不明文写入脚本和报告。
- 页面截图、接口报文及 AI 输入按数据等级处理。
- 阻断、豁免、基线更新等操作需要权限控制和审计。

### 8.5 兼容与扩展

- 规则结果采用统一模型，具体自动化工具可替换。
- 新应用接入主要依赖配置和适配，而不是复制整套系统。
- 预留与缺陷管理、流水线、消息通知和发布系统的集成能力。

## 9. 建议的轻量逻辑架构

1. **场景配置层**：应用、页面、链路、账号、数据、环境和基线。
2. **规则与门禁层**：指标定义、阈值、等级、通过逻辑和豁免。
3. **执行适配层**：核心流程、接口、性能、视觉等不同执行器。
4. **AI 辅助层**：场景推荐、探索走查、结果归纳和规则候选建议。
5. **结果与证据层**：统一结果模型、报告、截图、录像、日志和审计。
6. **流程集成层**：研发触发、流水线、提测、发布、缺陷及通知。

试点时以上可以是流水线任务加少量服务，不必一开始拆成多个独立系统。

## 10. 核心数据对象

建议至少统一以下对象：应用、页面、核心链路、检查规则、设计/截图基线、执行批次、单项结果、疑似问题、正式缺陷、豁免记录。

其中“执行批次”和“单项结果”必须关联代码版本、环境、规则版本及证据，避免后续无法复盘。

## 11. MVP 验收建议

MVP 不应只以“功能开发完成”为验收标准，至少应验证：

1. 试点核心链路可以自动执行并输出明确结果。
2. 注入一个已知问题后，对应规则能够识别并提供有效证据。
3. 环境异常和脚本异常不会被误判为产品缺陷。
4. 重复执行结果达到试点方认可的稳定程度。
5. 门禁报告能支持研发定位和复检。
6. 告警期完成误报、漏报、执行时长和维护工作量记录。
7. 需求方能够依据数据决定是否转强阻断及是否扩大范围。

具体数值目标应在现状采样后确定，不建议立项前直接承诺统一的误报率、执行时长或缺陷下降比例。
