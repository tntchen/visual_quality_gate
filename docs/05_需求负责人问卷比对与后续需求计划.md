# 需求负责人问卷比对与后续需求计划

- **分析日期**：2026-11-15
- **比对对象**：`docs/前端体验走查工具调查问卷.xlsx` 与 `docs/调查问卷/01_需求负责人版调查问卷.md`
- **填报身份**：项目负责人补充确认，本份问卷由需求负责人填写；工作簿未记录姓名
- **分析性质**：项目组分析建议，不是需求负责人对本文结论的再次确认

## 1. 总体结论

这份问卷已经明确了**业务价值方向和重点关注问题**，但尚未形成可以直接开发的一期需求基线。最核心的结论有五点：

1. **方向有价值，范围未收敛。** 需求负责人建议手机银行作为试点，关注基础体验、人工巡检、视觉、接口、生产问题和多版本覆盖，但又填写“本期不覆盖范围：暂无”。
2. **长期目标较完整，一期路径未决定。** `acb` 按问卷选项可解释为 A→C→B，即部门自测与报告准入、公司系统硬阻断、统一分析平台；需要确认这是长期演进顺序还是一期全部要求。
3. **试点对象较明确，试点流程不明确。** “设计、开发、测试”是研发阶段，不是可执行、可验收的用户业务操作流程。
4. **质量重点明确，但还不是可执行规则。** 三端一致性、视觉还原和加载体验需要拆成具体页面、设备、基线、指标、阈值和人工确认责任。
5. **线上表单与问卷模板不完全一致。** 四项模板内容未被线上采集，不能将空白解释为需求负责人默认接受。

因此，后续需求计划应采用“**先决策一期路径，再冻结一条流程和首批规则，随后开展技术验证**”，而不是直接按照全部回答启动完整系统开发。

## 4. 三个案例对需求计划的意义

### 案例一：页面与组件展示不一致

- **已暴露问题**：相同组件在不同业务页面存在设计细节差异，开发实现也不一致，UAT 才发现并导致版本暂停。
- **候选需求**：设计稿一致性检查、页面与确认基线比较、关键区域差异提醒。
- **前置条件**：明确“相同组件必须一致”与“因业务不同而允许不同”的规则；设计基线必须版本化，差异需人工仲裁。
- **不能直接假设**：所有视觉像素差异都属于缺陷，或 AI 可以代替设计验收。

### 案例二：iOS、安卓、鸿蒙三端不一致

- **已暴露问题**：页面细节、功能流程和机型兼容不一致，问题流入 UAT/SIT/生产。
- **候选需求**：三端页面一致性、核心流程一致性、指定机型兼容检查。
- **前置条件**：真实技术形态、设备矩阵、相同测试数据与操作步骤、一致性维度和合理差异清单。
- **不能直接假设**：浏览器扩展可以覆盖原生三端，或“三端完全一致”适用于所有页面。

### 案例三：动态编排页面加载缓慢

- **已暴露问题**：生产环境出现加载体验问题，希望提前分析并获得优化建议。
- **候选需求**：加载过程采集、明显退化提醒、慢加载证据和辅助归因。
- **前置条件**：页面与流程、设备/网络条件、指标定义、采样次数、基线和波动范围。
- **不能直接假设**：未采样就设置统一性能阈值，或一次慢加载就等于产品失败。

## 5. 可进入需求草案的内容

以下仅表示“有问卷依据，可提交访谈确认”，不是已经冻结：

1. 试点优先考察手机银行的面客体验场景。
2. 报告有效条件采用五项候选：对应当前代码/构建版本、覆盖约定核心流程、无必须修复问题、警告项已人工确认、失败后有复检记录。
3. 研发负责走查和整改，测试负责规则/业务风险/抽检，工具负责人维护采集、规则和报告。
4. AI 疑似问题需要人工确认。
5. 三个真实案例进入候选验收场景池。
6. 走查耗时在 PoC 中按实际流程采样，不预先承诺统一分钟数。

## 6. 推荐后续需求计划

### 6.1 第一步：完成一期路径决策

优先确认：

- A 是否为一期唯一主目标，C、B 是否作为后续独立阶段；
- 一期是否接受报告软门禁；
- 若 C 是一期强制要求，暂停部门工具全面开发，先评估公司系统写入、门禁、权限和跨部门立项路径。

**建议默认路径**：A 为一期，C/B 为条件性后续；AI 不直接控制门禁。该默认路径需需求负责人在访谈中明确确认。

### 6.2 第二步：冻结一个可验收试点

访谈后形成一页试点基线：

- 一个具体手机银行应用场景；
- 一条真实用户业务流程，包含入口、关键步骤和成功结果；
- 该流程的原生/H5/混合技术形态及三端覆盖范围；
- 首批页面、设备/机型和测试环境；
- 五至八项候选规则及明确非目标；
- 每项规则的输入、判定、证据、失败分类和人工责任人。

若技术形态暂时无法回答，不阻塞需求访谈，但必须登记应用负责人和补充日期，不能由项目组猜测。

### 6.3 第三步：分层建设首批规则

建议按可执行性分层，最终归属以访谈结论为准：

| 层级 | 候选内容 | 建议处理 |
|---|---|---|
| 基础闭环候选 | 页面无法访问/空白、主流程中断、未捕获异常、关键资源失败、接口 HTTP 失败或超时、版本和证据报告 | 优先形成确定性规则与报告闭环 |
| 三端/视觉专项 | 指定页面和区域的三端一致性、设计还原、合理差异和动态区域 | 先定义基线与一致性口径，再决定阻断或提醒 |
| 加载体验专项 | 指定流程的加载指标、慢加载证据和退化提醒 | 先采样建基线，再设阈值；优化建议可辅助生成 |
| AI 辅助 | 场景推荐、疑似问题补漏、摘要、脚本辅助 | 可关闭、需人工确认，不直接改门禁状态 |
| 后续独立评估 | 公司系统硬阻断、统一质量分析平台、全量自动巡检 | 不混入一期工作量，另行评估系统条件与价值 |

### 6.4 第四步：并行开展专项调查

- **应用与测试**：流程、页面、设备、账号、数据、历史缺陷和可复用自动化。
- **设计与研发**：视觉基线、业务允许差异、研发回检和设计争议仲裁。
- **架构与终端安全**：原生/H5 采集方式、安装权限、数据矩阵、部门机器和证据保存。
- **后端与接口**：业务成功字段、HTTP 与业务失败区别、环境异常分类。
- **研发协同接口负责人**：只读版本字段和手工降级；硬阻断仅在需求方坚持时另走能力评估。

### 6.5 第五步：冻结 PoC 需求与验收

PoC 开始前必须具备：

1. 一期目标和门禁路径有书面结论；
2. 一条真实流程和首批规则有责任人确认；
3. 三端、视觉、性能各自的专项口径已明确或被列为非目标；
4. 数据、终端和部门内分析不存在已知硬性不可行项；
5. 成功标准只有三项主指标，并有基线采集方式；
6. 报告核验、豁免、规则维护和争议裁决责任明确。

## 7. 建议的一期需求表述模板

> 面向手机银行【具体场景】的【一条核心流程】，验证研发/测试在提测前完成体验走查、部门内分析和可追溯报告闭环，由【最终核验角色】进行人工准入核验；一期覆盖【首批规则与端侧范围】，明确不覆盖【非目标】。AI 仅提供可人工确认的辅助结果，不直接决定提测。

该模板中的空格必须由访谈和专项调查填充，不能由 AI 代填。

## 8. 访谈后的计划分支

- **分支 A：接受一期软门禁。** 按本文计划收敛流程、规则和技术验证，形成 PoC 基线。
- **分支 B：硬阻断是一期必需。** 暂停当前部门工具实施设计，转为公司研发协同能力和跨部门立项评估；部门走查工具可作为独立子问题保留。
- **分支 C：三端/视觉必须一期阻断但基线不清。** 先开展专项样本验证，不承诺准确率和硬阻断时间；基础报告闭环可并行，但不得冒充三端专项已完成。
- **分支 D：所有目标都要求一期完成。** 标记范围无法收敛，由项目发起人和技术负责人重新评估资源、阶段与立项，不由两位开发直接承接全部范围。

20 分钟访谈的具体问法见 `docs/06_需求负责人远程访谈清单.md`。
