# 前端体验走查工具：问卷使用说明与回收汇总

## 1. 问卷包用途

本问卷包依据最新《需求方确认事项清单》编制，适用于立项准备阶段的自填问卷和专题访谈。

当前统一背景为：

- 工具服务零贷部门，先小范围试用，再评估部门推广；
- 公司研发协同系统目前只提供查询接口，不考虑业务插件和结果自动回传；
- 初步采用浏览器扩展采集，数据和分析均落地部门内机器；
- 一期优先考虑“有效走查报告作为提测准入依据”的部门软门禁；
- 需求细项和具体指标仍需根据问卷结果确认，问卷不代表已承诺建设全部功能。

## 2. 问卷版本及发放建议

| 文件 | 建议受访对象 | 主要确认内容 | 建议发放方式 |
|---|---|---|---|
| 01 需求负责人版 | 需求负责人、项目发起人、产品负责人 | 目标、价值、试点范围、报告准入、成功标准和责任 | 优先发放，最好结合访谈 |
| 02 研发与试点应用版 | 前端负责人、试点研发、应用负责人 | 核心流程、自测现状、环境账号、浏览器、版本和维护 | 需求方向初步明确后发放 |
| 03 测试负责人版 | 测试负责人、质量管理人员 | 历史缺陷、提测标准、报告证据、误报漏报和复检 | 与研发版并行 |
| 04 架构终端与安全版 | 架构师、终端管理、部门安全、运维、接口负责人 | 扩展权限、数据边界、本地部署、只读接口和 AI 条件 | 分角色填写对应章节 |
| 05 设计负责人版 | 设计负责人、视觉验收人员 | 设计基线、关键区域、合理差异和确认流程 | 需求包含 UI 还原时发放 |
| 06 后端与接口负责人版 | 后端负责人、核心接口责任人 | 业务成功规则、响应时间、异常场景和敏感字段 | 需求包含接口稳定性时发放 |

不要求每位受访者回答其他角色的专业问题。架构、终端和安全版可以由多人分节完成，不必强行安排一人填写全部内容。

## 3. 推荐使用顺序

### 第一步：先确认需求目标

优先使用需求负责人版，确认以下三个问题：

1. 首要目标是研发体验自测和报告准入，还是跨质量域统一分析；
2. 是否接受一期不自动阻断公司研发协同系统；
3. 试点用什么事实判断值得继续投入。

如果需求方坚持公司级自动阻断，应先暂停部门工具方案细化，转为确认公司系统能力和跨部门立项路径。

### 第二步：并行开展角色调查

- 研发版与测试版用于形成试点场景和规则草案；
- 架构、终端与安全版用于判断方案是否可安装、可采集、可部署；
- 设计版和后端版按实际指标范围发放。

### 第三步：用小样本验证关键答案

问卷答案只能作为输入，以下事项必须通过实际验证：

- 扩展能否在真实部门终端安装；
- 页面性能、Console、截图和接口数据能采集到什么程度；
- 数据能否在部门内完成脱敏、分析和报告闭环；
- 研发协同只读版本信息能否查询，查询失败能否手工降级；
- 测试能否根据报告完成一次提测核验。

### 第四步：召开澄清会并形成决策

不要直接把多份问卷原文作为需求结论。项目组应先整理一致意见、分歧和建议，再由有权决策的人确认。

## 4. 填写和回收注意事项

- 问卷中的“报告准入”均指部门软门禁，不是公司系统自动阻断。
- 涉及页面地址、账号、接口报文和客户数据时，问卷只记录类别及处理方式，不直接粘贴敏感内容。
- 材料通过行内认可的安全渠道提供，不要求受访者为了填写问卷复制敏感样例。
- 对“不知道”的回答，应记录需要补充的角色，不将空白视为默认同意。
- 多选题反映优先级时，建议要求受访者限定最多三项，避免所有事项都成为最高优先级。
- 问卷中的初步方案用于征求意见，不应让受访者误以为已经立项或完成技术选型。

## 9. 回收后应形成的立项输入

1. 一页目标及范围结论；
2. 试点应用、核心流程和页面清单；
3. 报告准入、复检及人工豁免流程；
4. 浏览器采集与部门内分析的可行性结论；
5. 数据项、权限、脱敏和保存边界；
6. 首批规则草案及明确不覆盖事项；
7. 小样本验证计划；
8. 责任分工、待决事项和试点成功标准。
