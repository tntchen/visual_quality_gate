## 1. 项目背景

传统前端体验检查主要依赖人工核验，存在以下问题：

- 检查标准受个人经验影响，不同研发自测深度不一致；
- 多版本、多分支持续交付时，人工巡检覆盖不足；
- 空白页、核心流程中断、接口异常、资源失败等基础问题可能流入测试；
- 性能下降、视觉差异及交互问题容易滞后发现；
- 重复巡检和回归占用研发、测试时间。

原始需求希望通过性能、视觉还原、交互规范、接口稳定性等指标建立体验质量基线，并利用 AI 自动化走查，将质量卡点前置到研发自测阶段。

经过系统边界分析，一期不宜直接建设公司级自动门禁或综合 AI 平台，而应先验证一个部门内可运行的最小闭环：

> 研发主动走查 → 浏览器扩展采集必要数据 → 部门内机器完成规则分析和留证 → 生成可追溯报告 → 测试或提测负责人核验报告。

## 3. 当前建议方案与待确认性质

以下是项目组建议的默认方向，不等于需求方已最终签字确认。

### 3.1 建议定位

**浏览器采集扩展＋部门内本地分析工具＋按需只读关联研发协同信息＋报告驱动的部门软门禁。**

“软门禁”在本项目中的含义是：研发提交有效走查报告，测试或指定提测负责人核验后进入测试；一期不由公司研发协同系统自动阻断。

### 3.2 如果需求方坚持自动阻断

当前系统边界无法支持该目标。必须先解决公司研发协同系统的写入、门禁和权限能力问题，必要时应调整立项路径。Work 不应通过部门工具绕过公司流程或模拟公司级硬阻断。

### 3.3 浏览器扩展的能力边界

浏览器扩展适合研发主动走查和低侵入采集，但不应默认承担：

- 无人值守定时回归；
- 全浏览器、全页面自动巡检；
- 完整 AI 分析和长期数据存储；
- 未经人工审核的自动提测判定。

特别需要注意：能够采集接口耗时和 HTTP 状态，不代表一定能在低权限条件下读取完整业务响应报文。无法获得业务成功字段时，结果应标记为“未判定”或“需人工确认”，不能将 HTTP 200 直接等同于业务成功。

## 4. 目标与非目标

### 4.1 一期目标

1. 验证浏览器扩展能否在真实部门终端受控安装并采集必要数据。
2. 验证数据能否在部门内机器完成脱敏、规则分析、证据保存和报告生成。
3. 用少量确定性规则提前发现基础体验问题。
4. 让失败结果具备截图、步骤、版本和环境等定位证据。
5. 验证测试是否愿意采用报告进行提测准入、复检和人工豁免。
6. 记录误报、漏报、执行耗时和维护成本，为是否扩大建设提供依据。

### 4.2 一期非目标

- 不建设研发协同业务插件、自动回传或公司级硬阻断；
- 不重复建设 SAST、SCA、代码质量扫描和单元测试；
- 不默认接入既有安全平台全量数据；
- 不建设跨所有质量域的统一分析平台；
- 不承诺无人值守、全浏览器、全量页面自动回归；
- 不依赖部门外 AI 或分析服务处理页面、报文和截图；
- 不用 AI 综合评分代替明确规则；
- 不一次性覆盖所有性能、视觉和交互指标；
- 不先建设大型微服务平台或复杂管理后台。

## 5. 建议逻辑架构

```text
研发人员
  │ 主动开始/结束走查、预览采集内容、补充版本信息
  ▼
浏览器采集扩展
  - 页面白名单和授权控制
  - 性能、接口元数据、Console、资源错误、操作步骤、截图
  - 必要的采集预览和脱敏
  │
  │ 本机或部门内网受控通信
  ▼
部门内分析端
  ├─ 数据接收、校验、脱敏和任务状态管理
  ├─ 确定性规则判断及失败分类
  ├─ 截图、原始证据和可选视觉基线管理
  ├─ 报告生成、复检和人工豁免记录
  └─ 可选的部门内 AI 辅助摘要/归因
  │
  ▼
测试或提测负责人
  - 核验报告、要求修复、复检或登记人工豁免

可选增强：
研发协同只读接口 ──→ 查询应用、分支、提交号、构建号等版本信息
查询不可用或权限不足 ──→ 手工录入/导入，不阻塞本地走查主流程
```

### 架构设计要求

- 采集端、规则判断、报告生成和存储职责分离，但一期可以部署为一个轻量本地应用。
- 优先复用部门既有技术标准和机器条件，不预设必须采用某种语言或框架。
- 若无其他约束，优先考虑单体本地应用、轻量数据库和受控文件存储，避免消息队列、微服务和分布式组件先行。
- 研发协同只读接口通过独立适配模块接入，主流程不得强依赖该接口。
- AI 是可关闭的辅助模块，不得成为基础走查和报告功能的运行前提。

## 6. 角色与核心流程

| 角色 | 主要操作 |
|---|---|
| 研发人员 | 配置或选择走查任务，主动开始/结束，预览采集内容，修复问题并复检 |
| 测试人员 | 维护或评审规则，核验报告，处理误报漏报，执行抽检和人工豁免 |
| 前端/应用负责人 | 维护核心流程、页面白名单、敏感区域和版本信息 |
| 设计人员 | 在启用视觉检查时确认基线、关键区域和争议差异 |
| 后端/接口负责人 | 确认业务成功规则、必要字段及环境异常边界 |
| 部门安全/终端管理 | 审批扩展权限、分发方式、本地部署和数据边界 |
| 工具维护人员 | 维护扩展、分析端、规则、报告模板和版本升级 |

### 核心使用流程

1. 研发选择应用、环境和核心流程，确认代码或构建版本。
2. 扩展检查页面是否在白名单内，研发主动开始走查。
3. 研发执行核心操作，扩展采集授权数据。
4. 研发结束走查并预览采集内容，必要时执行脱敏或补充说明。
5. 数据提交到部门内分析端，生成任务及规则检查结果。
6. 分析端区分产品失败、环境异常、采集失败和本地工具故障。
7. 研发查看失败证据并修复，随后按失败项或核心流程复检。
8. 测试核验有效报告，决定准入、退回或登记人工豁免。
9. 记录误报、漏报及维护事项，用于调整规则。

## 7. 建议 MVP 开发范围

建议先选择一个代表性应用、一至两条核心流程、不超过十个页面、五至八项确定性规则。

### 7.1 P0：必须形成的最小闭环

| 模块 | P0 能力 | 验收重点 |
|---|---|---|
| 应用与任务配置 | 应用、页面白名单、核心流程、环境、版本信息 | 配置可关联到一次走查 |
| 浏览器扩展基础 | 受控安装、开始/结束、状态提示、当前页面校验 | 非白名单页面不采集 |
| 基础采集 | 页面性能、接口元数据、Console、资源错误、操作步骤、截图 | 每项采集可解释、可关闭 |
| 采集确认 | 提交前预览，支持约定的脱敏或排除 | 研发知道提交了什么 |
| 本地分析 | 接收数据、任务状态、规则执行、失败分类 | 工具故障不能算产品缺陷 |
| 基础规则 | 页面访问异常、未捕获错误、关键资源失败、接口 HTTP 失败/超时、基础性能阈值或退化提醒 | 规则有明确输入和判定依据 |
| 证据与报告 | 版本、环境、步骤、截图、接口摘要、错误详情、规则版本 | 研发能据此开始定位 |
| 复检 | 对失败项或所在流程重新走查并保留历史 | 不覆盖首次失败记录 |
| 软门禁记录 | 报告状态、测试核验、人工退回及豁免 | 可追溯、不过度自动化 |
| 版本降级 | 只读查询失败时允许手工录入或导入 | 不影响本地走查闭环 |

### 7.2 P1：最小闭环稳定后选择验证

- 经授权的必要业务字段判断，不默认采集完整报文；
- 少量关键页面的视觉基线、动态区域遮罩和差异图；
- 部门内 AI 辅助失败摘要、重复问题聚类和疑似问题补漏；
- 按变更范围推荐走查任务；
- 多用户任务排队、存储管理和统一扩展分发。

### 7.3 结果状态必须统一

建议至少区分：

- `通过`：输入完整且满足规则；
- `产品失败`：证据表明产品不满足明确规则；
- `警告`：需要人工确认，不直接作为必须修复项；
- `未判定`：缺少业务字段、基线或其他必要输入；
- `环境失败`：测试环境、账号或依赖异常；
- `采集失败`：扩展权限、浏览器或采集中断；
- `工具失败`：本地分析、存储或报告模块异常；
- `已豁免`：经授权人工批准，记录原因和有效期。

不得把所有非通过状态简单合并为“产品不通过”。

## 8. 核心数据对象建议

| 对象 | 关键字段示例 |
|---|---|
| 应用 | 应用编号、名称、负责人、环境、状态 |
| 页面 | 页面编号、地址匹配规则、重要等级、白名单状态、敏感区域 |
| 核心流程 | 流程编号、步骤、预期业务结果、涉及角色、数据前置条件 |
| 规则 | 规则编号、类型、阈值、级别、适用范围、版本、启停状态 |
| 走查任务 | 任务编号、应用、流程、走查人、开始/结束时间、状态 |
| 版本上下文 | 分支、提交号、构建号、环境版本、来源（接口/手工）、确认人 |
| 单项结果 | 规则、状态、原始值、判定值、失败类型、说明 |
| 证据 | 截图、步骤、接口摘要、Console、性能数据、存储位置、脱敏状态 |
| 报告 | 报告编号、任务、规则版本、总体结果、有效期、核验状态 |
| 复检记录 | 原结果、复检任务、复检人、结论、时间 |
| 豁免记录 | 范围、原因、审批人、有效期、审计信息 |
| 视觉基线（可选） | 页面、设计版本、视口、截图、遮罩区域、确认人 |
| AI 反馈（可选） | 疑似问题、证据、置信说明、人工确认、误报标记 |

所有报告和单项结果必须能关联到应用、版本、环境、走查任务和规则版本。

## 9. 接口与集成要求

### 9.1 浏览器扩展与部门内分析端

具体协议由 Work 根据部门机器条件设计，但必须满足：

- 仅连接配置允许的本地或部门内地址；
- 有身份认证或等效保护措施，不能开放匿名本机接口；
- 传输内容有任务编号、数据类型、时间和扩展版本；
- 支持采集失败、分析失败和超时状态；
- 大数据及截图有大小限制、保存权限和保留策略；
- 通信失败不导致业务页面异常。

### 9.2 研发协同只读接口

一期只考虑按需查询，字段以真实接口文档为准。优先关注应用、分支、提交号、构建号、提测单号和环境信息。

设计要求：

- 独立适配，不将查询逻辑散落在报告和规则代码中；
- 权限不足、网络失败和字段缺失均有明确提示；
- 查询失败可手工降级，不能判定为产品失败；
- 不申请与一期无关的代码、安全扫描全量数据权限。

### 9.3 AI 接口

- 默认关闭或可替换；
- 只使用部门安全允许的模型和运行方式；
- 输入前执行数据最小化和脱敏；
- 保存模型版本、输入摘要和人工确认结果；
- AI 结果不得直接修改确定性规则、视觉基线或门禁状态。

## 10. 安全、权限与非功能要求

1. **页面白名单**：非授权页面不采集，扩展不得默认读取全部浏览历史或全部网站数据。
2. **主动走查**：开始和结束清晰可见，避免研发无感知持续采集。
3. **最小数据**：优先元数据和必要字段，完整报文不是默认要求。
4. **脱敏与预览**：敏感字段、截图区域和账号信息按规则处理。
5. **数据不出部门**：不得向未经批准的外部服务发送页面、报文、截图或日志。
6. **访问控制**：原始证据、报告、规则配置和豁免操作按角色授权。
7. **受控分发**：明确扩展签名、安装、版本升级、回滚和审计责任。
8. **证据保留**：配置原始数据、报告和日志的保留期及删除方式。
9. **稳定性**：同一版本、环境和数据条件下重复执行，结果差异应可解释。
10. **性能**：记录采集对页面的影响、本地分析耗时、并发和磁盘增长。
11. **降级**：扩展、只读接口或分析端故障时，有明确人工处理路径。
12. **可维护性**：规则、页面配置、流程步骤和报告模板尽量分离，避免写死。

## 11. 推荐开发顺序

### 阶段 0：开发前验证

在全面编码前完成：

- 需求方确认一期目标及是否接受报告软门禁；
- 确认试点应用、核心流程和首批规则；
- 在真实部门终端验证扩展安装和最小权限；
- 确认部门机器类型、资源、网络、端口和存储条件；
- 形成数据项—采集方式—权限—用途矩阵；
- 确认研发协同只读接口字段及手工降级方式。

**出口**：采集端和分析端不存在已知硬性不可行项。

### 阶段 1：可运行骨架

- 建立扩展和分析端最小工程；
- 使用模拟数据跑通任务创建、数据接收、规则执行和报告生成；
- 建立统一结果状态、核心数据对象和本地存储；
- 先证明端到端结构可运行，不在此阶段堆叠规则数量。

### 阶段 2：真实采集与基础规则

- 接入真实页面白名单和主动走查；
- 逐项接入性能、接口元数据、Console、资源错误、步骤和截图；
- 实现首批确定性规则、失败分类、脱敏和证据报告；
- 注入已知问题验证规则有效性；
- 重复执行并记录误报和采集稳定性。

### 阶段 3：报告准入试用

- 加入版本查询或手工补录；
- 实现报告核验、复检和人工豁免；
- 由研发、测试在一个试点应用中真实使用；
- 评价缺陷拦截、报告采用、耗时和维护成本。

### 阶段 4：按需扩展

只有前期闭环稳定后，才选择业务字段判断、视觉基线、AI 辅助、自动执行器或部门集中管理。

## 12. 首批验收场景

| 编号 | 验收场景 | 预期结果 |
|---|---|---|
| AT01 | 在非白名单页面尝试走查 | 不采集业务数据，并给出明确提示 |
| AT02 | 在授权页面开始、结束走查 | 状态清晰，生成唯一任务和采集清单 |
| AT03 | 注入一个未捕获脚本异常 | 对应规则失败，报告包含错误和截图 |
| AT04 | 注入一个关键资源失败 | 能区分资源失败与页面其他结果 |
| AT05 | 模拟接口 HTTP 失败或超时 | 能展示接口、耗时、状态和关联步骤 |
| AT06 | 出现 HTTP 200 但无业务成功字段 | 标记未判定或需人工确认，不直接判业务成功 |
| AT07 | 测试环境不可用 | 标记环境失败，不误判为产品缺陷 |
| AT08 | 扩展采集中断 | 标记采集失败，保留已采集状态及重试入口 |
| AT09 | 本地分析端故障 | 标记工具失败，不影响业务页面使用 |
| AT10 | 采集内容包含敏感字段 | 按规则脱敏或阻止提交，处理过程可追踪 |
| AT11 | 研发协同查询失败 | 可手工录入版本并继续走查 |
| AT12 | 修复后复检 | 保留首次失败及复检记录，不覆盖历史 |
| AT13 | 测试退回或人工豁免 | 报告记录原因、人员、范围和时间 |
| AT14 | 同一版本重复走查 | 结果稳定，差异有环境或数据解释 |
| AT15 | 检查网络及存储位置 | 页面、报文、截图和分析结果未流出批准边界 |

视觉基线和 AI 结果应另行设计专项验收，不与上述基础闭环混合验收。

## 13. 当前待确认事项及开发降级策略

| 待确认事项 | 为什么重要 | 未确认前的默认处理 |
|---|---|---|
| 需求方首要目标 | 决定是否为部门工具或统一平台 | 只按部门体验走查工具设计，不扩平台 |
| 是否接受报告软门禁 | 决定流程是否可落地 | 先实现报告和人工核验，不做自动阻断 |
| 试点应用及核心流程 | 决定真实采集和验收对象 | 使用模拟页面和模拟数据搭骨架 |
| 浏览器及扩展安装策略 | 可能直接决定扩展是否可用 | 先做真实终端最小验证，不写死浏览器能力 |
| 部门分析机器形态 | 决定本地应用或部门服务 | 优先轻量单机架构，暂不引入分布式组件 |
| 可采集数据及脱敏要求 | 决定权限、接口和报告内容 | 默认最少采集，完整报文不纳入基础范围 |
| 业务成功字段 | 决定接口业务判断深度 | 无字段时输出未判定，不用 HTTP 200 替代 |
| UI 设计基线 | 决定视觉比较是否可信 | 无确认基线时不做视觉阻断 |
| 部门内 AI 条件 | 决定 AI 是否可实施 | 基础版本不依赖 AI |
| 研发协同只读字段和权限 | 决定版本自动关联 | 保留手工录入，查询为增强能力 |
| 报告核验与豁免责任 | 决定软门禁是否有效 | 由需求、研发和测试负责人确认后启用 |
| 成功标准和阈值 | 决定试点评价 | 先采样，不在开发前虚构统一数值 |

## 14. 项目风险与停止扩大建设的条件

出现以下情况时，应暂停扩大范围并重新评估：

- 真实终端不允许安装扩展，且没有可行替代采集方式；
- 部门机器无法部署分析端或保存必要证据；
- 核心流程、测试账号或环境长期不稳定；
- 需求方不接受软门禁，又无法提供公司级硬门禁能力；
- 采集权限不足以支持已承诺指标，但需求范围不调整；
- 重复执行结果差异大，误报无法治理；
- 报告不能关联版本，测试无法信任其有效性；
- 只有报告数量增加，没有减少流入测试的问题；
- 研发、测试和工具团队均不承担后续维护责任。

## 15. 建议的第一开发迭代完成标准

第一迭代不追求功能齐全，只需证明：

1. 扩展可以在授权页面上主动开始和结束一次走查。
2. 至少一类真实数据可以从扩展传输到部门内分析端。
3. 分析端能用一条明确规则生成通过或失败结果。
4. 报告包含任务、版本、环境、规则、结果和必要证据。
5. 采集失败、环境失败和产品失败可以被区分。
6. 数据保存在批准的部门内位置，非白名单页面不被采集。
7. 测试能够查看报告并完成一次人工核验。

达到以上标准后，再扩展采集项和规则数量。

## 18. 交接后的第一项会议建议

建议 Work 项目负责人组织一次 60～90 分钟启动评审，参加人员包括需求负责人、测试负责人、试点前端负责人、架构师、终端/安全代表和后续开发人员。

会议只要求形成以下八项结论：

1. 一期是否确认为部门体验走查工具；
2. 是否接受报告软门禁；
3. 试点应用和一条核心流程；
4. 首批五至八项规则候选；
5. 真实浏览器和扩展验证方式；
6. 部门分析机器及数据保存位置；
7. 第一迭代开发和验收范围；
8. 待确认事项的责任人及完成日期。

会议结论形成后，再冻结 PoC 需求基线并进入完整开发。
