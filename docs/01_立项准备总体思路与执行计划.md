# 前端体验质量门禁：立项准备总体思路与执行计划

## 1. 文档目的

本文用于立项阶段的范围收敛、任务安排和决策准备，不直接作为开发说明书。后续应根据需求方确认结果和前期调查结论，形成正式的立项材料及试点方案。

建议项目名称暂定为“前端体验质量门禁与智能走查能力建设”，避免仅以“AI 走查智能体”或“统一质量分析平台”命名。前者容易偏离质量标准和交付流程，后者容易在目标未清时扩大建设边界。

### 1.1 已确认的行内基础条件与系统边界

- 行内已有研发协同系统，并集成代码质量扫描、代码安全扫描、Maven 单元测试等能力；目前只能提供查询接口，暂按不支持业务插件和结果写入处理。
- 行内已有专门的安全研发平台，具备 SAST、SCA 等静态及动态扫描机制，一期不重复建设也不默认接入其全量结果。
- 本工具服务零贷部门，前期在部门系统内试用，后续推广到整个部门，不以公司级系统改造为前提。
- 浏览器扩展可作为采集端，但页面、接口、截图及分析数据只能落地到部门内机器。
- 行内权限收口较紧，一期应最小化接口权限、浏览器权限、数据范围和跨系统依赖。
- 浏览器扩展能覆盖哪些数据、部门机器以何种方式部署，以及研发能否安装扩展，均需通过小样本验证。

### 1.2 当前定位判断

一期调整为 **“浏览器采集扩展＋部门内本地分析工具＋按需只读关联研发协同信息＋报告驱动的部门软门禁”**。

研发在授权页面上主动启动走查，扩展采集必要的性能、接口、页面异常、操作轨迹和截图；数据发送至部门内机器完成规则判断、证据保存和报告生成。研发协同系统仅在网络、认证和字段权限允许时查询应用、版本或构建信息，不能查询时可手工录入或导入，不阻塞主流程。

由于研发协同系统当前不支持插件和结果写入，一期不承诺自动回传或系统硬阻断。建议由测试或部门提测流程认可走查报告，形成“有报告才可提测”的软门禁；未来只有公司级系统开放相应能力后，再评估自动门禁。

浏览器扩展适合低侵入采集和研发自测，但不能默认等同于无人值守回归工具。核心链路自动回放、多浏览器定时巡检等能力，应在扩展可行性验证后另行判断是否需要部门内自动执行器。

## 2. 对需求的重新界定

结合最新边界，本需求建议拆成四层能力：

1. **浏览器采集端**：在研发主动授权的业务页面和走查时段内，采集必要的页面性能、接口元数据、前端异常、操作轨迹及截图；支持采集预览、脱敏和最小权限控制。
2. **部门内分析与留证**：在部门内机器完成确定性规则判断、视觉比较、报告生成和证据保存，数据不因 AI 或通用分析需要自动流出部门。
3. **只读上下文关联**：按需查询研发协同系统的应用、代码版本或构建信息；接口不可用或权限不足时，允许手工录入，不将其作为一期硬依赖。
4. **部门软门禁与 AI 辅助**：以可查验报告支持提测准入和测试抽检；AI 可在部门内辅助失败分类、结果摘要和补漏，不直接替代确定性门禁。

研发自测左移不等于取消测试职责。研发对提测前的基础质量负责，测试人员继续负责业务风险、测试设计、复杂场景、结果抽检和质量评价。

一期优先验证采集端和分析端能否闭环。研发协同查询属于增强项，SAST、SCA、单元测试等既有结果不属于一期必接范围。

## 3. 双视角分析

### 3.1 测试人员视角：重点不是“有没有工具”，而是“结果能不能信”

| 关注点 | 需要回答的问题 | 对立项方案的影响 |
|---|---|---|
| 测试对象 | 哪些应用、页面和核心链路必须覆盖，优先级如何划分 | 先建立场景资产，不追求一次性全量覆盖 |
| 判定标准 | 什么情况算失败，HTTP 200 是否代表业务成功，UI 差异多少算缺陷 | 建立指标字典和分档阈值 |
| 结果稳定性 | 同一版本重复执行是否得到相同结论，环境波动和脚本失败如何识别 | 必须设计重试、环境检查和失败分类 |
| 缺陷可定位性 | 失败后是否能提供截图、录像、接口报文、执行步骤和版本信息 | 报告和证据属于核心能力，不是附加功能 |
| 测试边界 | 研发自测、系统测试、回归测试分别使用哪些门禁 | 建议设置提测门禁和发布门禁两个节点 |
| 误报治理 | 视觉动态区域、性能抖动、第三方接口异常如何处理 | 建立基线、容差、豁免和责任人机制 |
| 维护成本 | 页面改版后由谁更新脚本、设计基线和测试数据 | 立项时明确长期运营责任 |
| AI 结果采用 | AI 发现的问题能否直接阻断，误报由谁确认 | 试点期 AI 以建议和补漏为主 |

测试人员应参与规则制定和验收，而不是只在平台建成后接收测试结果。

### 3.2 架构师视角：重点不是“AI 有多聪明”，而是“门禁能否稳定嵌入交付链路”

| 关注点 | 需要回答的问题 | 对立项方案的影响 |
|---|---|---|
| 系统边界 | 公司级协同只读、部门内试用、数据不出部门 | 采用部门内轻量工具，不依赖公司平台改造 |
| 浏览器采集可行性 | 目标浏览器是否允许扩展，所需数据是否能采集 | 先验证安装策略、接口元数据、报文和截图能力 |
| 本地部署形态 | 部门机器是个人办公机还是可常驻服务器 | 一期优先单部门分析节点或本地应用，按实际条件定型 |
| 软门禁流程 | 无法回传研发协同时如何约束提测 | 由测试或部门流程核验报告，不虚构系统硬阻断 |
| 规则与执行解耦 | 采集、指标定义和门禁判定是否混在一起 | 采集端、规则判定和报告分别管理 |
| 数据最小化 | 是否采集完整报文、页面内容和操作轨迹 | 默认最少采集、敏感字段脱敏、用户可预览 |
| AI 与硬门禁解耦 | AI 判断是否会影响确定性结果，数据是否出部门 | 优先部门内可用能力，AI 结果与确定性判定分通道 |
| 多应用复用 | 不同前端框架和部门系统如何接入 | 通过页面白名单、规则配置和统一结果格式复用 |
| 基线与版本 | 页面、设计稿、阈值和代码版本如何对应 | 所有结果关联应用及版本，版本允许手工补录 |
| 环境与依赖 | 测试账号、数据、后端依赖是否稳定 | 环境可用性检查应先于正式走查 |
| 安全与权限 | 扩展权限、本地端口、文件和报告访问是否可控 | 最小权限、受控分发、访问控制和操作审计 |
| 扩展与性能 | 本地分析资源能否支撑多人及大文件 | 记录处理时长、存储增长和并发瓶颈 |
| 可观测性 | 如何区分产品缺陷、采集失败、环境异常和本地工具故障 | 统一执行状态和失败原因分类 |

### 3.3 两种视角的共同结论

- 先证明采集可行、规则有效、结果稳定，再扩大覆盖面。
- 先验证浏览器扩展权限和部门内分析部署，再确定最终产品形态。
- 一期以报告驱动部门软门禁，不把公司级系统自动阻断作为前提。
- 先把少量高价值规则用于研发自测和提测准入，再考虑集中管理或跨工具分析。
- 门禁结果必须可解释、可复现、可追责。
- 研发协同只读接口和既有扫描结果均按需使用，不为“数据集中”而集中。
- AI 应降低走查、结果归因和脚本维护成本，且遵守数据不出部门边界。

## 4. 分阶段执行计划

以下周期为排期参考，需在现状调查后核定。

### 阶段 A：立项准备与现状调查（建议 1～2 周）

**目标**：把模糊需求转化为可评审的试点范围和问题清单。

主要工作：

1. 明确业务发起人、需求负责人、测试负责人、前端负责人和架构负责人。
2. 复盘近 6～12 个月体验类缺陷，按发现阶段、影响、原因和可自动识别性分类。
3. 调查应用清单、核心链路、前端技术栈、测试环境、设计资产和接口契约。
4. 专项确认目标浏览器及扩展安装策略、采集权限、敏感数据边界、部门机器部署条件和研发协同只读接口可用性。
5. 完成《门禁指标字典 V0.1》《试点范围建议》《需求决策清单》《数据采集及权限清单》和《部门软门禁流程》。
6. 对页面性能、接口元数据及必要报文、前端异常、截图、本地规则分析、报告生成和只读版本查询分别做小样本验证。

**阶段出口**：需求方能确认试点对象、首批指标、软门禁流程、数据边界、职责分工及试点成功标准；浏览器采集和部门内分析闭环经过实际验证。

### 阶段 B：技术验证 PoC（建议 2～3 周）

**目标**：验证“能跑、能判、能定位”，暂不以强阻断为目标。

建议范围：一个应用、一至两条核心链路、不超过十个页面、五至八项确定性规则。

主要工作：

- 跑通研发主动启动、结束和预览采集内容的浏览器扩展流程；
- 采集接口元数据及经授权的必要业务结果、前端异常、资源失败和基础性能数据；
- 在部门内机器完成规则判断，输出带截图、步骤、版本和环境信息的报告；
- 验证敏感字段脱敏、页面白名单、报告访问控制和本地数据保留；
- 选择少量页面验证视觉基线及动态区域处理；
- 验证研发协同只读版本查询，同时保留手工录入路径；
- AI 仅在部门内允许的条件下生成补漏或辅助归因结果，不直接阻断；
- 重复执行并记录误报、环境失败、采集失败、本地工具故障和处理时长。

**阶段出口**：核心规则结果可重复，失败证据足以支持研发定位，误报及维护成本处于试点方可接受范围。

### 阶段 C：试点接入交付流程（建议 3～4 周）

**目标**：验证门禁是否真正减少低级缺陷流入测试。

主要工作：

1. 在部门提测流程中试用“提交有效走查报告”的软门禁，先告警、后对少量 P0 项要求修复或豁免。
2. 明确报告编号、版本、有效期、复检和人工豁免规则，防止截图报告流于形式。
3. 测试人员抽检门禁结果，并跟踪提测后仍发现的体验缺陷。
4. 对比试点前后的提测一次通过率、低级缺陷数量和人工巡检耗时。
5. 评估是否增加发布前回归门禁。

**阶段出口**：试点方能证明质量收益大于执行和维护成本，并明确继续、调整或停止的结论。

### 阶段 D：推广与平台化（依据试点决策启动）

只有在试点证明价值后，再考虑部门内统一规则、受控扩展分发、视觉基线管理、多人任务和趋势分析等能力。若多人并发和集中管理超出单台部门机器承载能力，再论证部门级服务化部署。

公司级研发协同自动回传或硬门禁属于条件性后续事项，必须以公司系统开放能力和权限审批为前提；跨工具结果分析平台仍需另行论证，不作为部门推广的自然下一步。

## 5. 建议的 MVP 边界

### 纳入

- 一个代表性前端应用；
- 一至两条核心业务链路；
- 研发主动走查的核心流程、接口业务结果、前端异常、关键资源加载和基础性能；
- 浏览器扩展采集、采集预览、页面白名单及必要的脱敏；
- 部门内机器上的规则分析、证据保存和报告生成；
- 失败证据、重试及结果分类；
- 少量 P0 软门禁规则及人工豁免；
- 研发协同版本信息只读查询或手工补录；
- AI 补漏或失败归因的小范围验证，以部门内允许的能力为限。

### 暂不纳入

- 全公司所有应用和页面一次性接入；
- 所有体验指标全部阻断；
- 完全依靠 AI 自动生成并维护全部脚本；
- 用 AI 综合评分替代明确规则；
- 生产真实用户监控体系重建；
- 复杂跨端、全浏览器、全分辨率一次性覆盖；
- 研发协同业务插件、结果自动回传和公司级系统硬阻断；
- 重复建设 SAST、SCA、代码质量扫描、单元测试或通用安全报告能力；
- 接管既有安全门禁规则，或复制安全平台全量扫描数据；
- 依赖部门外 AI 或分析服务处理页面、报文和截图；
- 面向所有质量域的统一结果分析平台；
- 无人值守、全浏览器、全量页面的自动回归体系；
- 大规模独立平台和管理后台建设。

## 7. 立项与试点决策门

- **G0：可以启动 PoC**：试点范围明确，核心场景和环境可用，需求方接受部门软门禁，目标浏览器允许开展扩展验证，部门内分析机器落实。
- **G1：可以进入部门试用**：采集和规则可重复执行，失败可定位，敏感数据按规则脱敏，数据不出部门，已有报告复检和人工豁免机制。
- **G2：可以执行软阻断**：告警期数据证明规则稳定，P0 项均为明确底线问题，测试认可报告及豁免流程。
- **G3：可以推广到部门**：试点收益得到确认，扩展分发、版本升级、本地资源及维护责任可支撑多人使用。

## 8. 需要提前设定的调整或中止条件

出现以下情况时，不建议直接扩大建设：

- 核心链路、测试账号或环境长期不稳定，无法判断失败来源；
- 需求方无法确认哪些指标属于真正底线；
- UI 没有可确认的设计基线，却要求高准确率自动阻断；
- 重复执行结果差异大，误报无法通过规则治理降低；
- 门禁执行明显拖慢交付，且无法通过缩小范围或异步执行解决；
- 研发、测试和应用团队均不承担后续规则及脚本维护；
- 试点只增加报告数量，没有减少流入测试或生产的缺陷。

## 9. 立项准备完成后的成果包

1. 需求范围及决策记录；
2. 历史缺陷复盘与自动化机会清单；
3. 试点应用、页面和核心链路清单；
4. 门禁指标字典 V0.1；
5. 现状调查及技术验证报告；
6. 浏览器采集端、部门内分析端及只读关联的轻量架构；
7. 浏览器权限、数据采集、脱敏、本地部署和软门禁验证结论；
8. PoC/试点计划、风险清单和职责分工；
9. 试点成功标准及后续推广决策条件。
