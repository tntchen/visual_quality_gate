# 一期初始需求草案

- **文档版本**：V0.1
- **编制日期**：2026-11-22
- **文档状态**：初始草案，待需求方、设计、研发、测试及安全相关角色评审
- **试点业务域**：手机银行卡片开发业务，具体卡片场景与页面范围待确认
- **一期主需求**：在提测前通过代码扫描，比对 UE 设计与 UI 规范，输出可定位、可解释、可人工复核的不符合项
- **使用边界**：本文用于需求评审和 PoC 准备，不是已冻结的开发范围、技术选型、排期或验收承诺

## 0. 当前优先级最高的待确认项

以下事项直接决定一期需求能否从“初始草案”转为“可开发、可验收的 PoC 基线”。未关闭前可以开展草案评审和模拟样本研究，但不应据此承诺真实代码覆盖范围、准确率或开发排期。

| 顺序 | 待确认项 | 当前缺口 | 必须形成的输出 | 建议责任角色 |
|---|---|---|---|---|
| 1 | **UE 设计与 UI 规范是否可用** | UE 规范仍在沉淀；尚未明确设计输入是结构化设计文件、组件定义、设计变量，还是图片和过程文档 | 一个试点场景的 UE 样例、对应 UI 规范、版本信息、可读取字段清单；李炜已认领寻找相关文档，完成日期待补 | 设计／UE 负责人，需求负责人协调 |
| 2 | **代码范围及代码—UE 对应关系** | 尚未明确试点代码仓库、模块、组件、技术形态，以及代码组件与 UE 页面／组件如何对应 | 一个试点场景的“代码文件／组件—UE 页面／组件—设计版本”映射表；无法映射的处理规则 | 卡片业务研发、客户端／前端负责人、设计负责人 |
| 3 | **首批可执行规则与判定样本** | “编码规范、还原度、兼容性”仍是主题，尚未转成明确的检查对象、预期值和允许差异 | 首批规则清单；每条规则的依据、输入、判定逻辑、严重级别；已确认的正例、反例和争议样本 | 设计、研发、测试、工具维护人员共同评审 |
| 4 | **一期边界与最终人工责任** | 静态代码检查与真实终端验证的边界、报告最终核验人、设计争议裁决人、AI 与人工分界尚未完整确认 | P0／P1／后续／非目标清单；报告核验及争议处理流程；AI 只辅助的人工确认节点 | 需求负责人、测试负责人、设计负责人 |
| 5 | **代码与数据的安全使用条件** | 代码只读权限、部门内分析机器、UE 资产保存、结果访问和保留方式尚未确认 | 代码及设计资产的权限来源、批准部署位置、访问控制、保留与删除要求；不得依赖未经批准的外部 AI 或云服务 | 架构／安全、研发协同接口负责人、工具维护人员 |

**当前最高优先级不是选择扫描框架，而是取得一套真实但可安全使用的“代码＋UE＋UI 规范”样例，并验证三者能否建立明确对应关系。**

## 1. 背景与当前需求结论

### 1.1 业务背景

手机银行卡片业务需要在 App 三端及 H5 等多端环境展示。既有问卷和会议输入重点关注卡片编码规范、设计还原度以及不同机型的兼容表现，希望将问题发现时点前移至研发和提测前阶段。

### 1.2 当前需求方向

1. 一期优先支持研发自测并输出人工报告，暂不接入公司研发协同系统的自动阻断。
2. 一期试点聚焦手机银行卡片开发业务，而不是一开始覆盖全部手机银行应用。
3. 需求方明确希望以代码扫描为主路径，提前比对代码实现、UE 设计和 UI 规范，输出不符合点。
4. App／浏览器插件不再作为一期主闭环的必要前提；如后续需要验证真实渲染、动态数据或运行兼容性，可作为独立补充方案另行评估。
5. 现有 UE 设计规范尚未完全沉淀，首批规则必须依据实际设计资产和业务经验共同定义。

### 1.3 对“代码比对 UE”的需求解释

本草案默认其含义为：

> 从代码中提取组件、样式、布局约束和状态等可检查事实，与对应 UE 设计属性及 UI 规则进行版本化比较，并解释差异依据。

它不等于“代码直接与设计图片做像素比较”。若实际只能提供图片或截图，需要单独评估图像理解方案、误差和人工复核成本，不得沿用结构化设计比较的准确率假设。

## 2. 一期目标与非目标

### 2.1 一期目标

1. 在提测前发现代码层面可确定的 UE 还原和 UI 规范不符合项。
2. 建立代码版本、UE 版本、UI 规则版本和检查结果之间的可追溯关系。
3. 输出能够帮助研发定位的报告，包括代码位置、实际实现、预期要求和判定依据。
4. 支持人工复核、争议处理、研发整改和复检，保留历史记录。
5. 通过试点记录有效问题、误报、未判定原因、使用耗时和维护成本，为后续扩展提供依据。

### 2.2 一期非目标（草案建议，待评审）

- 不建设公司研发协同业务插件、结果自动回传或公司级硬阻断。
- 不重复建设通用代码质量、安全扫描、SAST、SCA 或单元测试能力。
- 不承诺仅靠静态代码扫描覆盖真实渲染、运行异常、接口成功、加载性能和全部机型兼容性。
- 不默认覆盖手机银行全部业务、全部代码仓库、全部 UE 页面和全部 UI 规范。
- 不把 AI 输出直接作为不符合定论或提测门禁结果。
- 不将 App／浏览器插件采集作为一期基础闭环的运行依赖。
- 不依赖部门外 AI 或云服务处理代码、UE 设计、截图和分析结果。

## 3. 试点范围

### 3.1 草案范围内

- 一个经需求方确认的卡片业务代表场景；具体页面和组件待第 0 章事项关闭后填写。
- 与该场景对应且获授权的代码仓库、模块和版本。
- 对应版本的 UE 设计资产及已评审 UI 规范。
- 首批可从代码中稳定提取、从设计或规范中获得明确预期值的规则。
- 差异结果、证据、人工复核、整改和复检报告。

### 3.2 条件性范围

以下内容只有在样本验证证明可解释、可重复后，才可逐项纳入：

- 业务二次封装组件和公共组件的递归解析；
- 动态样式、主题变量、继承样式和运行时组装属性；
- 动态编排或服务端下发内容；
- Android、iOS、鸿蒙和 H5 的分端规则；
- AI 辅助建立代码—UE 映射、解释差异或推荐整改；
- 插件或自动化截图提供的真实终端补充证据。

条件性内容无法判断时必须输出“未判定”及原因，不得猜测符合或不符合。

### 3.3 明确留待后续评估

- 全应用、全页面、全仓库的自动扫描；
- 无人值守的全量巡检和公司级统一质量平台；
- 以静态扫描替代全部测试、设计验收和真机兼容测试；
- 公司研发协同系统自动硬阻断；
- 未经专项验证的视觉图片理解或 AI 自动验收。

## 4. 输入与对应关系要求

### 4.1 代码输入

- 来源必须只读、经过授权并记录代码版本。
- 能定位到试点场景涉及的文件、模块和组件。
- 记录无法解析的语法、生成代码、动态配置及外部依赖，不将其静默忽略为“通过”。
- 真实代码和配置不得发送到未经批准的外部服务。

### 4.2 UE 设计输入

- 每个设计对象必须具有页面／组件标识和设计版本。
- 尽可能取得组件类型、颜色、字体、字号、间距、圆角、尺寸、布局和状态等结构化属性。
- 若属性缺失、设计版本不明或只有图片，应明确限制可执行的规则范围。
- 设计变更必须产生可识别的新版本，不得覆盖历史依据。

### 4.3 UI 规范输入

- 规范必须能追溯到条款、示例或经确认的业务经验。
- 自然语言规范转为可执行规则后，需由设计和业务相关责任人评审。
- 规则需说明适用范围、允许差异、严重级别和版本。
- 规范之间冲突时保留冲突并提交人工裁决，不由工具自行选择。

### 4.4 代码—UE—规则映射

每次检查至少关联：

> 业务场景／代码版本／代码组件 ↔ UE 页面或组件／设计版本 ↔ UI 规则／规则版本

无法建立唯一映射时，结果进入“未判定”或“需人工确认”，不得自动匹配到相似页面后直接判为产品问题。

## 6. 规则、结果与报告要求

### 6.1 规则定义

每条规则至少包含：

- 规则编号、名称、版本和启停状态；
- 适用业务、端、组件和代码范围；
- 需要提取的代码事实；
- UE 预期属性或 UI 规范条款；
- 比较逻辑、允许差异和严重程度；
- 所需证据、缺失输入处理方式及责任角色。

### 6.2 结果状态

沿用项目统一状态，不因引入代码扫描而合并失败类型：

| 状态 | 本需求中的含义 |
|---|---|
| `通过` | 输入和映射完整，代码事实满足明确规则 |
| `产品失败` | 证据充分，代码实现不满足明确规则 |
| `警告` | 疑似问题或需人工确认，不直接作为必须修复定论 |
| `未判定` | 缺少 UE 属性、映射、规则或其他必要输入 |
| `环境失败` | 代码、设计服务、依赖或批准环境异常 |
| `采集失败` | 代码读取、UE 获取或解析过程中断 |
| `工具失败` | 分析、存储或报告模块自身异常 |
| `已豁免` | 经授权人工批准，记录原因、范围和有效期 |

AI 产生的疑似问题不得绕过人工确认直接变为“产品失败”。

### 6.3 单项结果与报告

每个不符合项应尽量包含：

- 业务场景、代码文件、组件和可取得的位置；
- 当前代码值、实现方式或提取事实；
- 对应的 UE 预期值或 UI 规范条款；
- 差异说明、规则编号和严重级别；
- 代码版本、UE 版本、规则版本和检查时间；
- 证据、结果状态、人工复核和整改复检记录。

总体报告应同时列出通过项、不符合项、警告、未判定和检查覆盖缺口，不能只展示问题数量而隐藏未检查范围。

## 7. 核心使用流程与角色

### 7.1 核心流程

1. 研发选择试点场景、只读代码版本和对应 UE 版本。
2. 系统校验代码、UE、UI 规则及映射是否满足检查条件。
3. 系统提取代码事实并记录无法解析或无法映射的内容。
4. 确定性规则执行比较，生成单项结果和覆盖缺口。
5. 系统输出报告；AI 辅助内容如启用，必须单独标识。
6. 研发查看并整改明确问题，争议项提交指定人员复核。
7. 研发发起复检，系统保留首次结果和复检历史。
8. 测试或最终指定角色按待确认流程核验报告。

### 7.2 角色分工

| 角色 | 草案职责 |
|---|---|
| 卡片业务研发 | 提供代码范围和映射信息，处理不符合项并发起复检 |
| 设计／UE 负责人 | 提供设计资产和版本，确认设计属性、允许差异及争议结果 |
| 需求负责人 | 确认试点业务、一期目标、范围和非目标 |
| 测试／质量负责人 | 参与规则及样本评审，验证报告可用性，按确认后的职责核验结果 |
| 工具维护人员 | 维护代码读取、解析、规则执行、报告和版本升级 |
| 架构／安全及相关接口负责人 | 确认只读权限、批准部署位置、数据边界和访问控制 |

最终报告核验人、规则争议裁决人和长期维护团队仍待明确，本表不构成责任承诺。

## 8. 安全与非功能要求

1. **只读与最小权限**：只访问试点所需代码、UE 和规范，不修改业务代码或公司研发协同状态。
2. **部门内处理**：代码、UE、截图、报告和分析数据只能进入批准的部门内机器与服务。
3. **可解释性**：每个产品失败必须能追溯到明确规则、实际值和预期依据。
4. **可重复性**：同一代码、UE 和规则版本重复检查，结果差异必须可解释。
5. **故障隔离**：输入缺失、环境异常、解析失败和工具故障不得误算为产品缺陷。
6. **访问与保留**：代码上下文、UE 资产、报告和日志按角色授权；保存位置、保留期、删除和备份方式待确认。
7. **AI 可关闭**：关闭 AI 后，代码读取、确定性规则和基础报告仍可运行。
8. **可维护性**：规则、映射、解析和报告模板分离，避免将业务规范写死在不可审查的逻辑中。

## 9. PoC 验证与初始验收场景

### 9.1 PoC 目标

使用一个真实卡片代表场景的一套获批样例，证明“代码＋UE＋UI 规范”能够建立映射，并通过少量明确规则输出可定位报告。PoC 不预设扫描框架、语言、模型或全端覆盖。

### 9.2 初始验收场景

| 编号 | 场景 | 预期结果 |
|---|---|---|
| AC-01 | 输入完整的代码、UE 和规则版本 | 生成可追溯报告，覆盖范围清晰 |
| AC-02 | 样本中存在一个已确认的不符合项 | 检出该问题，并给出代码位置、实际值、预期值和依据 |
| AC-03 | 输入已确认的符合样本 | 不因主观推断产生产品失败 |
| AC-04 | 缺少 UE 属性或代码—UE 映射 | 输出未判定及缺失原因，不猜测结论 |
| AC-05 | 代码版本与 UE 版本无法确认对应 | 阻止直接判定或要求人工确认版本关系 |
| AC-06 | 样式由运行时或动态配置决定且静态证据不足 | 标明未判定和所需补充证据 |
| AC-07 | 代码或 UE 读取失败 | 区分环境失败／采集失败，不算产品失败 |
| AC-08 | 分析或报告模块故障 | 标记工具失败，不影响业务代码和公司系统 |
| AC-09 | 修复后执行复检 | 保留首次不符合和复检结果，不覆盖历史 |
| AC-10 | 关闭可选 AI | 基础确定性检查和报告仍可完成 |
| AC-11 | 检查网络、权限及存储位置 | 代码、UE 和报告未流出批准边界，业务代码保持只读 |

具体准确率、召回率、耗时和误报阈值必须在样本验证后由相关责任人确定，本草案不虚构数值。

## 10. 试点评价指标

需求方尚未从既有问卷中选定三项主成功指标。建议从以下候选中评审，不在本草案中预设目标值：

- 已知不符合项的有效检出情况；
- 误报、漏报和未判定的构成及原因；
- 报告能否帮助研发直接开始定位；
- 单次检查耗时和研发整改复检成本；
- 规则、映射及设计版本变化的维护成本；
- 试点研发和测试对报告的实际采用情况；
- 提测后同类 UI 问题的变化。

## 11. 转为 PoC 需求基线的条件

只有以下条件具备后，才将本草案升级为可开发、可验收的 PoC 基线：

1. 第 0 章五项高优先级待确认事项均有结论，或有明确的责任人、完成日期和经批准的范围降级。
2. 一个具体卡片场景及其代码、UE、UI 规范和映射样例已评审。
3. 首批规则、正例、反例、争议样本及非目标已确认。
4. 静态检查与真实终端补充验证的边界已确认，不以静态结果冒充实际渲染结论。
5. 代码和数据安全条件不存在已知硬性不可行项。
6. 报告核验、争议裁决、规则维护和复检责任已明确。
7. 三项主成功指标及其采样方式已确认。
