# 前端体验质量门禁：前期调查方向与参与人员建议

## 1. 调查目标

前期调查不是编制大而全的现状报告，而是回答四个立项问题：

1. 哪些真实问题最值得自动化拦截；
2. 现有资产能否支撑轻量试点；
3. 哪些环境或规则问题会使门禁失效；
4. 试点需要哪些人投入，后续由谁维护。

建议采用“材料查阅＋关键人员访谈＋小样本实测”，避免只发问卷、不做验证。

## 2. 前期调查方向

### 调查一：历史缺陷与质量成本

**目的**：从真实事故反推首批规则，而不是从工具功能反推需求。

调查内容：

- 抽取近 6～12 个月前端体验类缺陷、提测驳回和生产问题；
- 记录问题类型、发现阶段、影响范围、定位耗时、修复耗时和发现方式；
- 区分核心流程、接口、性能、视觉、交互、浏览器兼容及环境类问题；
- 判断每类问题能否通过确定性规则识别，是否适合 AI 辅助；
- 统计人工巡检和回归的主要耗时环节。

**建议输出**：《历史缺陷复盘及自动化机会清单》，至少包含“典型缺陷—应前置节点—候选规则—所需证据—预计维护成本”。

### 调查二：研发交付及门禁流程

**目的**：确定门禁真正能嵌入的位置。

调查内容：

- 代码提交、构建、部署、提测、回归、发布和紧急发布流程；
- 当前是否已有质量门禁、研发自测和测试准入标准；
- 研发提测时如何证明已自测，测试是否认可外部工具报告；
- 公司研发协同只读接口可提供哪些应用、代码版本、分支和构建信息；
- 代码版本、测试环境版本和发布版本如何关联，接口不可用时如何手工补录；
- 部门内报告编号、复检、人工豁免和审计如何形成闭环；
- 若未来需要公司级硬门禁，还缺少哪些系统能力，但不将其列为一期依赖。

**建议输出**：现状流程图及部门软门禁目标流程图，标明走查、报告、提测核验、复检和人工豁免位置，并注明研发协同仅提供只读上下文。

### 调查三：应用、页面与核心链路

**目的**：选择有代表性且具备试点条件的对象。

调查内容：

- 应用业务量、变更频率、历史缺陷和体验敏感度；
- 核心链路是否清晰，是否跨系统、跨角色或依赖外部服务；
- 页面分级、路由、访问权限和终端类型；
- 是否包含微前端、App 内 H5、小程序、SSO、复杂报表等特殊场景；
- 应用团队是否有稳定人员参与试点和维护。

**试点选择建议**：优先“问题较典型、链路清晰、环境稳定、团队愿意配合”的应用，不必一开始就选技术最复杂或业务最大的应用。

### 调查四：前端技术与可测试性

**目的**：评估自动执行及后续维护成本。

调查内容：

- 前端框架、组件库、路由、构建方式及浏览器支持范围；
- 页面元素是否有稳定标识，是否大量依赖动态样式或坐标定位；
- 已有单元、组件、端到端及接口自动化资产；
- 动画、懒加载、异步渲染、验证码和文件上传下载等难点；
- 是否能提供测试模式、数据准备接口、mock 或稳定测试标识；
- 当前脚本失败的主要原因和维护工作量。

**建议输出**：技术难点清单、可复用脚本清单及需要研发配合改造的最小事项。

### 调查五：接口契约与依赖环境

**目的**：确保能判断“业务真的成功”，并区分产品问题和环境问题。

调查内容：

- 核心接口清单、业务返回码、字段契约和超时定义；
- 页面操作与接口请求的关联方式；
- 后端、第三方、短信、支付、风控等依赖的测试可用性；
- 测试数据准备、清理、恢复及账号权限；
- 环境发布频率、可用性和故障通知机制；
- 报文、截图和日志的数据敏感等级。

**建议输出**：核心接口判定表、依赖清单、环境前置检查项及数据安全约束。

### 调查六：性能基线与采集条件

**目的**：判断性能门禁是否具备可重复性。

调查内容：

- 当前是否采集 Web 性能、接口性能或真实用户性能；
- 测试机、网络、浏览器、缓存和数据量是否固定；
- 不同页面的合理性能目标和历史波动；
- 性能采集对页面及流水线的影响；
- 是否需要比较上一稳定版本，基线如何保存。

**建议输出**：性能现状采样、波动来源、指标定义及阈值制定建议。没有采样前，不建议直接承诺统一阈值。

### 调查七：设计资产与视觉验收

**目的**：确认 UI 还原度是否有可信判断依据。

调查内容：

- 设计稿是否完整、及时更新并与开发版本对应；
- 是否有统一组件库、标注和视觉验收规范；
- 当前由谁进行 UI 验收，常见争议是什么；
- 动态数据、时间、轮播、个性化内容如何处理；
- 不同浏览器和分辨率是否允许合理差异；
- 设计人员能否参与基线确认及差异复核。

**建议输出**：关键页面视觉基线样本、动态区域清单、容差原则和设计确认流程。

### 调查八：浏览器扩展、部门机器与 AI 条件

**目的**：验证采集端和分析端能否在银行终端及数据权限约束下形成闭环。

调查内容：

- 目标浏览器类型、版本、扩展机制、企业终端安装策略、签名分发和升级方式；
- 扩展可申请的页面、网络、调试、截图和存储权限，以及安全审批要求；
- 性能指标、接口元数据、响应报文、Console、操作轨迹和截图分别可采集到什么程度；
- 页面注入对业务页面的影响，是否可采用只读或被动采集方式；
- 部门机器的操作系统、CPU、内存、磁盘、网络、常驻和备份条件；
- 本地服务或桌面应用能否安装，端口、进程和文件权限是否受限；
- 浏览器版本、字体和显示缩放对截图基线的影响；
- 部门内可用的模型或 AI 运行环境，页面、报文和截图是否允许作为输入；
- 原始数据、报告及日志的脱敏、加密、访问控制和保留要求。

**建议输出**：《数据项—采集方式—权限—用途矩阵》《部门内部署条件清单》《扩展分发及安全约束》《技术验证范围》。

### 调查九：研发协同只读关联及数据边界专项

**目的**：将公司级系统依赖降到最低，明确哪些信息值得查询、哪些数据不得流入部门工具。

调查内容：

- 研发协同只读接口的认证、网络访问、字段权限、调用频率及申请周期；
- 能否按应用、代码版本、分支或构建号查询最小必要上下文；
- 接口不可用时的手工录入、导入和报告版本确认方式；
- 是否需要查询代码质量、安全扫描或单元测试状态，具体用于哪条部门规则；
- 没有明确使用规则时，不接入 SAST、SCA 等全量结果；
- 部门机器、浏览器扩展和研发协同接口之间的数据流向及权限边界；
- 查询失败不得影响本地走查主流程，也不得被误判为产品质量失败；
- 公司级系统未来开放写入或门禁能力仅作为后续观察项，不作为一期工作量承诺。

**建议输出**：《只读接口及字段清单》《数据流向与权限边界》《手工补录降级方案》，并附一次最小只读查询验证记录；若权限短期无法申请，可先以模拟数据验证。

### 调查十：运营责任与成本

**目的**：防止只计算建设成本，不计算持续使用成本。

调查内容：

- 规则、脚本、测试数据、设计基线和白名单分别由谁维护；
- 页面变更时如何同步更新；
- 失败分类、误报复核和豁免审批由谁负责；
- 每次全量执行及单次变更检查的大致耗时；
- 报告、录像和日志保留成本；
- 新应用接入需要多少支持工作。

**建议输出**：RACI、运营流程和成本项清单。试点期间应记录实际维护工作量。

## 3. 建议开展的五项小样本技术验证

| 验证项 | 最小做法 | 主要判断点 |
|---|---|---|
| 扩展安装及最小采集 | 在真实部门终端安装验证扩展，仅采集一个授权页面的性能、Console 和截图 | 安装及权限是否可行，采集是否影响页面 |
| 接口与前端异常采集 | 验证接口元数据及经授权的必要响应内容，关联页面步骤和 Console | 是否能支持业务失败判断，哪些数据必须降级 |
| 部门内分析闭环 | 将采集数据传到部门机器，完成脱敏、规则判断和报告生成 | 数据是否不出部门，失败是否能定位 |
| 性能与视觉采样 | 同页多次采集性能及截图，制造一处明确差异 | 波动和误报是否可控 |
| 只读版本关联及软门禁 | 查询或手工录入版本，生成报告并由测试完成一次提测核验 | 报告能否关联版本并支持部门流程 |

验证结果应同时记录成功和失败案例，不只保留演示效果最好的一次。

## 4. 架构路线调查与选择建议

### 路线 A：浏览器采集扩展＋部门内分析端＋报告软门禁（一期推荐）

**适用**：研发在本地完成自测，目标浏览器允许安装受控扩展，部门内具备一台可运行分析工具及保存报告的机器。

**分工**：扩展只在授权页面和走查时段采集必要数据；部门内分析端负责脱敏、确定性规则判断、视觉比较、证据和报告；测试或提测负责人核验报告。研发协同只读接口仅补充版本信息，不可用时手工录入。

**优点**：跨系统依赖最少，符合数据不出部门要求，可快速验证研发自测价值。

**限制**：以研发主动走查为主，不能默认承担无人值守回归；软门禁需要部门流程配合，报告必须关联版本并可复检。

### 路线 B：浏览器扩展＋部门内自动执行器＋分析端（按回归需要补充）

**适用**：试点后证明有价值，并出现定时回归、无人值守、多页面批量执行或核心链路重复回放需求。

**分工**：扩展继续服务研发本地自测，自动执行器承担受控批量任务，二者复用部门内规则和报告能力。

**优点**：兼顾低侵入采集和稳定回归。

**代价**：需要额外执行节点、浏览器环境、测试数据和脚本维护，不能在一期默认打包建设。

### 路线 C：部门级集中管理与分析服务（多人推广需要时演进）

**适用**：多人、多应用使用后，单台机器在并发、存储、集中基线、扩展分发或权限管理方面出现明确瓶颈。

**优点**：便于部门内统一规则、基线、版本和报告管理。

**代价**：增加服务部署、权限、备份、高可用和运维责任，仍需遵守数据不出部门边界。

### 公司级集成及跨工具分析的定位

研发协同自动回传、硬门禁以及跨 SAST、SCA、单元测试的统一分析均不作为一期路线。只有公司系统能力、权限和需求方目标发生变化，并出现明确使用规则时，才重新评估。

### AI 的定位

AI 是部门内分析端的可选辅助能力，用于受控探索、失败分类、重复问题聚类和报告摘要。页面、报文和截图不得因为 AI 分析自动离开部门；AI 不直接控制门禁。

**推荐顺序**：先验证路线 A；确有无人值守回归需求再补路线 B；多人推广出现实际管理瓶颈后再采用路线 C。

## 5. 建议参与人员

### 5.1 核心工作组（建议保持精简）

| 角色 | 建议投入职责 | 必须参与的关键活动 |

| 需求负责人/项目发起人 | 确认目标、范围、资源和争议裁决 | 立项、范围确认、试点决策 |
| 测试负责人 | 牵头缺陷复盘、指标、门禁及验收 | 全阶段，尤其规则和结果稳定性 |
| 前端负责人/试点应用负责人 | 提供场景、技术约束并落实研发配合 | 场景梳理、技术验证、问题整改 |
| 架构师 | 控制系统边界、集成方式、扩展及安全 | 现状调查、路线选择、方案评审 |
| 测试开发或自动化工程师 | 执行核心链路及证据采集验证 | PoC、误报及维护成本评估 |
| 浏览器扩展/前端工具工程师 | 验证扩展权限、数据采集、页面兼容及受控分发 | 采集验证、扩展开发及升级 |
| 部门内分析端工程师（可由前端或测试开发兼任） | 实现本地规则、脱敏、证据和报告闭环 | 本地部署、分析及资源验证 |
| 终端管理/部门运维 | 确认扩展安装策略、部门机器、进程端口和存储条件 | 终端验证、部署及部门推广 |
| DevOps/流水线工程师（按需要） | 提供构建版本、测试环境及后续自动执行条件 | 只读关联和后续自动回归评估 |

## 7. 建议的轻量协作节奏

- **一次启动会**：确认目标、试点候选、角色和材料清单。
- **两次专题会**：分别讨论“缺陷与规则”“架构、环境与流程”。
- **一次小样本验证评审**：展示重复执行、失败证据和误报，不只演示成功路径。
- **一次立项决策会**：确认是否进入 PoC、范围、责任和成功标准。
- 准备期间用一个决策清单跟踪争议，避免建立复杂项目管理机制。

## 8. 启动后前五个工作日建议

### 第 1 天：确定范围与人员

确认需求负责人、核心工作组、试点候选应用和材料清单。

### 第 2～3 天：缺陷复盘与现状调查

选择典型历史问题，梳理现有流程、工具、环境、设计和接口资产；同步确认真实浏览器扩展安装策略、部门分析机器及研发协同只读接口条件。

### 第 3～4 天：形成规则草案并做小样本验证

将典型缺陷映射为候选规则，同时验证一个授权页面的最小采集、本地分析、报告生成及版本查询或手工补录。若接口文档与真实行为不一致，以实际验证记录为准。

### 第 5 天：召开需求澄清及立项准备评审

确认试点范围、软门禁原则、采集和本地数据边界、AI 边界、成功标准、责任分工和待决事项。

## 9. 调查结束时应能回答的问题

- 为什么选这个应用和这些链路试点；
- 首批每条规则分别能拦截哪些历史问题；
- 哪些结果可硬阻断，哪些只能告警或观察；
- 为什么当前环境能支持可重复执行；
- 哪些现有工具可复用，新增建设最小范围是什么；
- 浏览器扩展能否安装，各数据项需要什么权限，哪些内容无法采集；
- 部门内机器能否完成脱敏、规则分析、证据和报告闭环；
- 研发协同只读接口提供哪些版本信息，不可用时如何降级；
- 测试是否认可报告软门禁，如何防止报告与代码版本脱节；
- 既有安全及代码扫描结果哪些确有使用规则，哪些明确不进入本项目；
- AI 在试点中具体承担什么任务，如何做到数据不出部门并控制成本；
- 谁负责规则、脚本、基线、环境和平台维护；
- 用什么数据决定继续、调整或停止。
