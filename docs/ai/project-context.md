# AI 项目上下文

- **项目暂定名**：前端体验走查与提测准入辅助工具
- **服务范围**：零贷部门，先小范围试用，再评估部门推广
- **当前阶段**：立项准备、需求澄清与技术验证前
- **本文更新时间**：2026-11-22
- **本文性质**：基于现有资料的派生摘要，不替代原始需求与正式决策

## 1. 当前已确认事实

以下来自 `docs/00_Work系统开发项目交接文档.md` 的 C01～C08：

1. 公司已有研发协同系统，包含代码质量、代码安全和 Maven 单元测试等能力，本项目不重复建设。
2. 研发协同系统当前只提供查询接口，业务插件预计不支持，一期不依赖结果自动回传。
3. 公司已有安全研发平台，具备 SAST、SCA 等能力，本项目不接管其门禁，也不默认复制全量结果。
4. 本工具服务零贷部门，一期是部门级轻量工具，不是公司级平台。
5. 行内权限收口严格，必须最小化浏览器权限、接口权限、数据范围和跨系统依赖。
6. 浏览器扩展是当前较合适的候选采集形式，但真实浏览器和安装策略仍须验证。
7. 页面、接口、截图和分析数据只能落在部门内批准的机器，不得因外部 AI 或云服务自动离开部门。
8. 需求方目标尚未完全澄清，不能把硬阻断、UI 还原和 AI 自由探索全部默认纳入一期。

## 2. 当前主需求与建议方案，不是最终承诺

2026-11-16 会议将一期方向推进为：优先支持研发自测并输出人工报告，暂不接入公司协同阻断；试点聚焦手机银行卡片开发业务。2026-11-22 项目组进一步补充明确：需求方希望以代码扫描形式，在提测前比对 UE 设计和 UI 规范并输出不符合点。

因此，当前主需求闭环调整为：

> 只读代码＋对应 UE 设计＋UI 规范 → 建立代码—UE—规则映射 → 确定性规则比较 → 输出可定位差异报告 → 人工复核、整改和复检。

App／浏览器插件不再是一期主闭环的必要前提，只在后续需要真实渲染、动态数据或运行兼容证据时作为独立补充方案评估。静态代码检查不得冒充真实终端视觉效果或全部机型兼容性结论。

当前建议优先取得一个卡片场景的“代码＋UE＋UI 规范”真实获批样例，验证结构化属性、映射和首批规则。AI 仍是可关闭的辅助模块，不能成为基础检查和报告功能的运行前提。完整草案见 `docs/07_一期初始需求草案.md`，其内容尚未冻结为开发或验收基线。

### 3.2 三个真实案例

1. 多页面使用相同组件但因设计细节和实现不同导致展示不一致，在 UAT 发现并造成版本暂停。
2. iOS、安卓、鸿蒙三端页面细节、功能流程及机型兼容不一致，在 UAT/SIT/生产发现，造成投诉、返工和测试资源浪费。
3. 动态编排页面加载缓慢，在生产发现，希望提前进行加载分析并给出优化建议。

这些案例适合用于反推候选规则和验证场景，但尚不能直接等同于一期验收范围。

## 4. 当前必须保留的未决分歧

1. **草案与正式基线**：会议已形成一期人工报告、卡片业务和代码扫描方向，但 AI 纪要仍需参会决策人确认，初始需求草案尚未冻结。
2. **UE／UI 资产可执行性**：设计输入的结构化程度、版本和规范条款尚未明确，不能默认代码可以直接与设计图片稳定比较。
3. **代码—UE 映射与首批规则**：具体卡片场景、代码范围、组件映射、允许差异及正反例尚未评审。
4. **静态检查与运行验证边界**：代码扫描不能替代真实渲染、动态数据和全部机型兼容验证；是否需要插件或截图补充证据留待专项评估。
5. **AI 辅助与人工判定**：AI 可辅助映射、解释和整改建议，但不得直接修改规则或形成门禁定论；人工确认节点仍需写入流程。
6. **职责、安全和成功标准**：报告最终核验人、设计争议裁决人、长期维护责任、代码只读权限、部门部署和三项主成功指标仍待确认。

## 6. 统一术语

- **软门禁**：研发提交有效报告，由测试或指定负责人核验后进入测试；不是公司系统自动阻断。
- **候选需求**：从早期拆解、问卷或访谈收集的待评估事项。
- **已确认约束**：当前设计不得绕过的真实系统和组织边界。
- **正式决策**：由有权的人类决策人确认，并记录日期、范围和依据的结论。
- **未判定**：缺少业务字段、基线或其他必要输入，不能推断通过或产品失败。
