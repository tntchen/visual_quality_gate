# 工程约束与验证基线

本文将原始资料中的工程约束集中给后续开发使用。当前没有已选定的语言和框架，以下内容是设计边界，不是技术选型结果。

> **2026-11-22 路线更新**：一期主需求已调整为“代码扫描比对 UE 设计与 UI 规范并输出不符合项”，见 `docs/07_一期初始需求草案.md`。本文中的浏览器扩展、主动走查和第一迭代流程属于早期工程参考；公司系统只读、部门内数据处理、最小权限、统一失败状态和 AI 不直接控制门禁等硬约束继续有效。具体工程流程以评审后的 PoC 基线为准。

## 1. 建议逻辑模块

```text
研发人员
  │ 主动开始/结束、预览采集、补充版本
  ▼
受控采集端（浏览器扩展为候选，不预设覆盖原生三端）
  │ 白名单、最小权限、必要数据与截图
  ▼
部门内分析端
  ├─ 数据接收、校验、脱敏、任务状态
  ├─ 确定性规则与统一结果状态
  ├─ 证据、报告、复检和人工豁免
  ├─ 独立只读版本适配及手工降级
  └─ 可关闭的部门内 AI 辅助（可选）
  ▼
测试或指定提测负责人核验
```

职责需要分离，但一期可以部署为一个轻量本地应用。没有实际并发、存储或管理瓶颈前，不引入分布式组件。

## 2. 当前禁止的建设方向

- 公司研发协同业务插件、自动回传或通过部门工具模拟公司硬阻断；
- 重复建设代码质量、安全扫描、SAST、SCA 和单元测试；
- 跨所有质量域的统一分析平台；
- 默认无人值守、全客户端、全页面自动回归；
- 依赖部门外 AI 或云服务处理页面、报文、截图和分析数据；
- 以 AI 综合评分替代明确规则；
- 在真实需求未收敛前建设大型微服务体系或复杂管理后台。

若正式决策改变以上范围，应先记录决策及其系统、权限和安全前提，再修改本文件。

## 3. 数据与安全

1. 非白名单页面不采集；开始和结束状态必须清晰可见。
2. 默认只采集元数据和必要字段，完整报文不是基础要求。
3. 提交前提供采集预览、约定的脱敏或排除能力，并保留处理记录。
4. 扩展只连接允许的本地或部门内地址，通信需要认证或等效保护，不得开放匿名本机接口。
5. 原始证据、报告、规则和豁免按角色授权；保存位置、保留期、删除和备份方式待确认。
6. 真实账号、令牌、客户数据、页面报文、业务截图和运行证据不得进入 Git。
7. AI 编程助手同样属于数据处理通道。未经批准，不把敏感代码、内部文档、真实配置或业务数据发送给外部服务。
8. `.gitignore` 只能降低误提交概率，不能替代人工检查和行内安全控制。

## 4. 判定规则

- 每条规则必须有明确输入、阈值或判定逻辑、适用范围、版本、证据和失败分类。
- HTTP 状态与业务结果分开；没有经确认的业务成功字段时输出“未判定”或“需人工确认”。
- 不用自动重试掩盖失败，首次与重试结果都要保留。
- 工具故障不能统计为产品失败，环境异常不能统计为产品缺陷。
- 视觉差异必须有经确认的基线、视口、动态区域和容差；无基线时不做视觉阻断。
- AI 输出只能作为疑似问题和辅助建议，保留模型版本、输入摘要、证据和人工确认结果。

统一结果至少包括：

| 状态 | 含义 |
|---|---|
| `通过` | 输入完整且满足明确规则 |
| `产品失败` | 证据表明产品不满足明确规则 |
| `警告` | 需要人工确认，不直接作为必须修复项 |
| `未判定` | 缺少必要输入，无法可靠判断 |
| `环境失败` | 测试环境、账号或依赖异常 |
| `采集失败` | 权限、客户端或采集中断 |
| `工具失败` | 本地分析、存储或报告模块异常 |
| `已豁免` | 经授权人工批准，记录原因、范围和有效期 |

## 5. 可追溯性

每次报告和单项结果至少关联：

- 应用、流程、页面和环境；
- 代码/构建版本及其来源（只读接口或手工）；
- 走查任务、人员和时间；
- 规则编号与规则版本；
- 原始值、判定值、结果状态和失败类型；
- 必要步骤、截图、接口摘要、Console 或性能证据；
- 复检、核验和豁免历史。

首次失败和复检历史不得互相覆盖。只读版本查询失败时允许手工补录，但不能把查询失败判成产品失败。

## 6. 技术选型原则

需求与终端条件确认后，再按以下标准选型：

1. 真实终端可安装、可签名、可升级、可回滚；
2. 部门内网依赖可获取，构建和运行不依赖未经批准的外部服务；
3. 两位开发都能维护，调试和测试成本可接受；
4. 采集、规则、报告和存储可独立测试；
5. 优先轻量单体和轻量存储，避免不必要的运维负担；
6. 第三方依赖的许可、安全、版本和长期维护情况明确；
7. AI 可替换、可关闭，基础闭环不依赖 AI。

重要选型通过 ADR 记录备选方案和取舍，不由某个 AI 工具默认决定。

## 7. 验证策略

### 当前文档阶段

- 检查 Markdown 相对链接、编号、文档状态和相互引用；
- 检查事实是否来自原始资料，建议与决策是否分开；
- 检查是否意外写入敏感信息或虚构环境参数。

### 后续 PoC 与代码阶段

- 单元测试：规则、状态映射、脱敏、数据校验和报告模型；
- 集成测试：采集端到分析端、存储、版本适配及手工降级；
- 故障注入：环境不可用、采集中断、分析故障、接口超时和敏感字段；
- 重复性验证：同版本同环境多次执行，差异必须可解释；
- 真实终端验证：安装、权限、页面影响、通信、存储和升级；
- 安全验证：非白名单不采集、匿名访问被拒绝、证据不出批准边界；
- 报告验收：研发能定位，测试能核验，历史能复检。

验收优先参考交接文档 AT01～AT15。视觉、AI 和三端场景需要另行定义专项验收，不能混入基础闭环后降低结果可解释性。

## 8. 第一迭代建议出口

在范围得到确认后，第一迭代只证明：一次授权页面主动走查、一类真实数据采集、一条确定性规则、一份可追溯报告，以及产品失败、环境失败、采集失败和工具失败的可区分性。若手机银行技术验证推翻浏览器扩展路线，应先记录路线决策，再确定等价的最小迭代。
