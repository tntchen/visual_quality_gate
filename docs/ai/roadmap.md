# 项目路线图与近期工作

- **更新时间**：2026-11-15
- **当前阶段**：阶段 0，需求澄清与开发前验证
- **当前建议**：先形成可评审的 PoC 基线，再建立代码骨架

本文是工作建议，不代表已批准的排期或人员承诺。

## 2. 建议的启动澄清会

建议 60～90 分钟，需求、测试、试点前端/客户端、架构、终端/安全和后续两位开发参加。除交接文档原有八项结论外，重点追加：

1. 问卷填写人的角色及 `acb` 的准确含义；
2. 手机银行具体技术形态，三端一致性问题发生在原生页面、H5 还是混合场景；
3. 将“设计、开发、测试”改写为一条真实用户业务操作流程；
4. 三端一致性、视觉和加载体验是否全部属于一期，哪些只观察或留作后续；
5. AI“直接判断提测”与“必须人工确认”的关系；
6. “开发完成回检”的具体责任含义，设计基线由谁提供和确认；
7. 软门禁不能接受时，是否具备公司系统硬阻断的现实条件。

会议输出必须包含决策人、日期和待办责任人，不能只写“已讨论”。

## 3. 阶段划分

### 阶段 0：开发前验证

- 完成上述澄清和材料回收；
- 在真实终端验证最小采集能力；
- 确认部门内分析、脱敏、证据保存和报告条件；
- 建立数据项—采集方式—权限—用途矩阵；
- 验证研发协同只读字段及手工降级。

**出口**：目标和试点范围明确，采集端与分析端不存在已知硬性不可行项，PoC 基线得到确认。

### 阶段 1：可运行骨架

- 根据已评审技术选型建立采集端和分析端最小工程；
- 使用模拟数据跑通任务、接收、规则、报告和统一状态；
- 建立本地存储、测试和基础工程规范。

**出口**：端到端结构可运行，不依赖真实外部接口或 AI。

### 阶段 2：真实采集与基础规则

- 接入白名单和主动走查；
- 逐项接入获批数据；
- 实现首批规则、失败分类、脱敏和证据报告；
- 通过故障注入和重复执行验证有效性。

**出口**：规则结果稳定、失败可定位、敏感数据和失败状态处理符合约束。

### 阶段 3：报告准入试用

- 加入版本查询或手工补录；
- 实现报告核验、复检和人工豁免；
- 在一个试点应用中记录质量收益、耗时和维护成本。

**出口**：试点方能依据数据决定继续、调整或停止。

### 阶段 4：按需扩展

只有前期闭环稳定后，才评估业务字段判断、视觉基线、AI 辅助、自动执行器、三端专项能力或部门集中管理。公司级硬阻断和统一质量分析平台需要独立评估其系统能力和立项前提。

## 4. 当前明确不做

- 不直接根据早期需求细项生成完整应用；
- 不预设浏览器扩展可以覆盖 iOS、安卓、鸿蒙原生页面；
- 不在未确认基线前实现视觉硬阻断；
- 不在未确认部署和模型条件前引入 AI 运行依赖；
- 不为了展示进度虚构阈值、成功率、性能指标或终端验证结果。
