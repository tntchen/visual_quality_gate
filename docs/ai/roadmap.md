2026-11-16 已开展手机银行 UI 质检方案研讨，形成一期人工报告、卡片业务试点和代码预检讨论方向。2026-11-22 项目组补充明确代码扫描比对 UE 与 UI 规范为一期主需求，据此编制 `docs/07_一期初始需求草案.md`。

## 3. 阶段划分

### 阶段 0：开发前验证

- 关闭初始需求草案第 0 章的高优先级待确认事项；
- 获取一个试点场景的代码、UE、UI 规范和版本样例；
- 验证代码事实提取、代码—UE 映射和首批规则可判定性；
- 确认部门内分析、访问控制、证据保存和报告条件；
- 明确静态代码检查与真实终端补充验证的边界。

**出口**：目标和试点范围明确，代码、UE、规则及部署不存在已知硬性不可行项，PoC 基线得到确认。

### 阶段 1：可运行骨架

- 根据已评审技术选型建立代码输入、解析、规则和报告最小工程；
- 使用模拟数据跑通版本上下文、映射、规则执行、报告和统一状态；
- 建立本地存储、测试和基础工程规范。

**出口**：端到端结构可运行，不依赖真实外部接口或 AI。

### 阶段 2：真实样例与首批规则

- 接入获批的只读代码、UE 和 UI 规则；
- 实现首批确定性规则、失败分类和差异报告；
- 使用已确认正例、反例和争议样本验证有效性；
- 通过故障注入和重复执行验证稳定性及未判定处理。

**出口**：规则结果稳定、问题可定位、未判定可解释，敏感数据和失败状态处理符合约束。

### 阶段 3：报告试用

- 实现人工复核、整改、复检和必要的豁免记录；
- 在一个卡片试点场景中记录有效问题、误报、耗时和维护成本；
- 由研发、测试及设计按确认后的职责使用和评价报告。

**出口**：试点方能依据数据决定继续、调整或停止。

### 阶段 4：按需扩展

只有前期闭环稳定后，才评估更多业务与代码仓库、AI 辅助映射和解释、插件或自动化截图等真实终端补充验证，以及部门集中管理。公司级硬阻断和统一质量分析平台需要独立评估其系统能力和立项前提。

## 4. 当前明确不做

- 不直接根据早期需求细项或本草案生成完整应用；
- 不把 App／浏览器插件作为一期主闭环的必要前提；
- 不用静态代码扫描冒充真实渲染、动态数据和全部机型兼容结论；
- 不重复建设通用代码质量、安全扫描、SAST、SCA 或单元测试能力；
- 不在未确认部署和模型条件前引入 AI 运行依赖；
- 不为了展示进度虚构阈值、准确率、性能指标或真实样例验证结果。
