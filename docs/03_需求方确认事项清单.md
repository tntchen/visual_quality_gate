# 前端体验质量门禁：需求方确认事项清单

## 1. 使用说明

本清单用于立项访谈、需求澄清会和试点评审。建议逐项记录结论、决策人和日期，不要只记录“已沟通”。

优先级说明：

- **A：立项或启动 PoC 前必须明确**，否则范围和责任无法收敛。
- **B：PoC 设计前明确**，否则无法形成可执行规则。
- **C：转强阻断或推广前明确**，可在试点过程中逐步确定。

## 2. 原需求中需要重点澄清的表述

| 原表述 | 模糊点 | 建议确认方向 |
|---|---|---|
| “统一复用的体验质量基线” | 统一到什么范围，不同应用是否同阈值 | 统一指标定义和结果格式，阈值按页面等级及场景分档 |
| “AI 自动化走查智能体进行指标测试” | AI 是执行工具、判定工具还是辅助分析工具 | 确定性规则负责门禁，AI 负责补漏和提效 |
| “而非依赖于测试人员” | 测试人员是否退出规则制定和质量验收 | 研发承担提测前自测，测试负责规则、业务风险和抽检 |
| “达标后方可进入测试、上线等环节” | 一个门禁还是多个门禁，谁触发、谁豁免 | 分设提测门禁和发布门禁，分别定义范围 |
| “UI 还原度” | 以设计稿、线上旧版还是 AI 审美为准 | 以确认后的设计基线为准，AI 主观评价不直接阻断 |
| “接口响应时间” | 平均值、最大值还是分位值，什么环境下测 | 统一采样口径，核心接口可分档设置 P95 等阈值 |
| “巡检潜在问题” | 潜在问题是否直接形成缺陷或阻断 | 先输出疑似问题和证据，经人工确认后闭环 |

## 3. A 类：立项或启动 PoC 前必须确认

| 编号 | 需要确认的问题 | 为什么必须确认 | 建议默认方案 | 建议决策人 |
|---|---|---|---|---|
| A01 | 本需求最主要解决的是低级缺陷流入测试、回归耗时，还是生产体验事故 | 决定首批规则和收益指标 | 优先减少核心链路低级缺陷及人工重复巡检 | 需求负责人、测试负责人 |
| A02 | 试点应用、核心链路和页面范围是什么 | 没有范围就无法评估工作量 | 一个应用、一至两条链路、不超过十个页面 | 需求负责人、应用负责人 |
| A03 | 哪些历史问题最能体现建设价值 | 防止凭想象设计指标 | 选取近 6～12 个月典型缺陷反查规则 | 测试负责人 |
| A04 | 提测门禁和发布门禁是否都需要 | 两个节点目标及严格程度不同 | MVP 先做提测门禁，发布门禁试点后评估 | 需求、研发、测试负责人 |
| A05 | 哪些问题允许直接阻断 | 阻断会直接影响交付 | 仅空白页、核心链路中断等明确底线问题 | 需求、测试、研发负责人 |
| A06 | 研发、测试、设计、平台团队分别承担什么职责 | 防止平台建成后无人维护 | 测试共管规则，研发维护业务场景，平台维护公共能力 | 各团队负责人 |
| A07 | 试点成功用什么事实判断 | 避免只以功能上线作为成功 | 稳定性、拦截效果、误报、耗时和维护成本综合评价 | 需求负责人 |
| A08 | 是否接受先告警、后阻断 | 直接阻断可能因误报失败 | 原则上接受，告警期数据作为阻断依据 | 研发、测试、发布负责人 |
| A09 | AI 是否允许直接决定门禁通过与否 | 影响门禁可信度 | MVP 不允许，AI 只输出疑似问题及建议 | 需求、测试、架构负责人 |
| A10 | 测试环境、账号和核心依赖是否具备基本稳定性 | 环境不稳会导致结果无法解释 | 环境可用性作为 PoC 前置条件 | 应用、后端、测试负责人 |
| A11 | 是否已有可复用的自动化、流水线和报告能力 | 决定轻量接入还是新建能力 | 优先复用现有资产，不重复建设 | 架构、DevOps、测试负责人 |
| A12 | 是否涉及敏感页面、客户数据、生产账号或外部 AI 服务 | 影响部署、权限及数据方案 | 使用测试数据和最小权限账号，先完成安全边界确认 | 安全、架构、应用负责人 |
| A13 | 项目发起人及最终争议裁决人是谁 | 阈值和阻断争议需要快速决策 | 指定一名业务需求负责人和一名技术负责人 | 立项发起人 |
| A14 | 长期运营归哪个团队 | 防止把持续维护误认为一次性开发 | 试点期即明确规则、脚本、平台和基线责任人 | 立项发起人、各团队负责人 |
| A15 | 项目目标究竟是部门前端体验自测与软门禁，还是跨质量域统一分析平台 | 两者范围、数据和组织投入差异很大 | 一期只做部门前端体验自测及提测准入，统一分析平台另行论证 | 立项发起人、需求负责人 |
| A16 | 需求方是否接受一期不自动回传、不自动阻断研发协同系统 | 当前公司系统只读且不支持业务插件，硬门禁缺少系统条件 | 以部门内有效报告作为软门禁，未来再评估公司级集成 | 需求、研发、测试负责人 |
| A17 | 部门提测流程由谁核验报告，报告有效期和人工豁免如何执行 | 软门禁没有流程约束会退化为自愿工具 | 测试或指定提测负责人核验，报告关联版本并可复检 | 测试、研发、发布负责人 |
| A18 | 既有代码质量、安全扫描和单元测试结果是否与本项目存在明确组合规则 | 当前无自动集成必要，防止无边界汇聚数据 | 没有明确规则则一期不接，只保持各自独立结果 | 需求、测试、架构负责人 |
| A19 | 目标浏览器类型、版本及扩展安装策略是什么 | 浏览器扩展方案可能受终端策略直接限制 | 先做真实终端安装及采集验证，不假定所有浏览器可用 | 终端管理、前端、架构负责人 |
| A20 | 部门内分析机器是个人办公机、专用机器还是部门服务器 | 决定部署、并发、常驻、存储和运维方式 | 一期优先一台受控部门分析节点，按实际条件验证 | 部门负责人、架构、运维 |
| A21 | 部门机器能否访问研发协同只读接口，认证及字段权限如何申请 | 只读接口也可能存在网络和数据权限约束 | 查询仅作增强，不可用时手工录入版本信息 | 架构、研发协同接口负责人 |
| A22 | 页面、接口报文、截图和操作轨迹中哪些数据允许采集和保存 | 银行数据敏感，浏览器采集权限高 | 默认最少采集、白名单、脱敏、预览和本地留证 | 部门安全、应用、测试负责人 |
| A23 | 数据及 AI 分析是否均不得离开部门，部门内可用何种模型或运行环境 | 决定 AI 是否可用以及部署成本 | 不将部门外 AI 作为依赖，先完成确定性规则闭环 | 部门安全、架构、需求负责人 |
| A24 | 扩展由谁签名、分发、升级和审计 | 部门推广需要受控终端管理，不能依赖个人手动装包 | 试点期即明确分发和版本责任人 | 终端管理、前端、部门负责人 |
| A25 | 项目成功按质量收益还是按功能及数据接入数量评价 | 防止以“接了多少工具”替代实际价值 | 按缺陷前置、结果稳定、报告采用和维护成本评价 | 立项发起人、需求负责人 |

## 4. B 类：PoC 设计前确认

### 4.1 场景与覆盖范围

| 编号 | 需要确认的问题 | 建议输出 |
|---|---|---|
| B01 | 核心链路的起点、终点和成功业务结果是什么 | 链路步骤及预期结果说明 |
| B02 | 哪些页面属于核心页面，哪些只做普通巡检 | 页面分级清单 |
| B03 | 需要覆盖哪些浏览器、分辨率和终端 | 覆盖矩阵及不覆盖范围 |
| B04 | 是否包含 App 内 H5、小程序、微前端或跨系统跳转 | 特殊技术场景清单 |
| B05 | 测试账号涉及哪些角色，数据如何准备和恢复 | 账号、角色、数据及前置条件 |
| B06 | 第三方接口、验证码、短信、支付等环节如何处理 | mock、白名单或专用测试方案 |

### 4.2 指标与判定

| 编号 | 需要确认的问题 | 建议输出 |
|---|---|---|
| B07 | 页面性能具体使用哪些指标，采样点和环境是什么 | 性能指标定义及采样口径 |
| B08 | 阈值是防明显退化，还是追求统一优秀水平 | 门禁目标及分档阈值原则 |
| B09 | 核心接口的业务成功码和关键字段由谁确认 | 接口业务判定清单 |
| B10 | 响应时间按单次、平均还是分位值判断，样本量多少 | 接口性能统计口径 |
| B11 | 哪些 Console Error 和资源失败可以忽略 | 白名单及有效期规则 |
| B12 | UI 基线来自设计稿、组件规范还是已确认截图 | 基线来源及确认流程 |
| B13 | 哪些区域属于关键视觉区域，哪些动态区域需要遮罩 | 区域及容差配置 |
| B14 | 视觉差异由谁认定，设计人员是否有确认时限 | 视觉问题处理流程 |
| B15 | 是否检查加载、空数据、异常、无权限等状态 | 状态场景清单 |
| B16 | 门禁失败后的复检范围是什么 | 单项、单链路或全量复检规则 |

### 4.3 AI 走查

| 编号 | 需要确认的问题 | 建议输出 |
|---|---|---|
| B17 | AI 首批主要解决场景推荐、自由探索、报告归因还是脚本辅助 | AI 能力优先级，避免同时展开 |
| B18 | AI 走查允许操作到什么范围，是否禁止真实提交或写操作 | 操作权限和安全边界 |
| B19 | 疑似问题需要哪些证据才可转正式缺陷 | AI 结果采用标准 |
| B20 | AI 产生的误报由谁标记，是否计入质量收益 | 反馈及统计口径 |
| B21 | AI 输入是否允许包含源代码、设计稿、截图和接口报文 | 数据使用边界 |

### 4.4 浏览器采集、本地分析与只读关联

| 编号 | 需要确认的问题 | 建议输出 |
|---|---|---|
| B22 | 走查由研发手动启动还是扩展可自动开始，如何限定页面和时长 | 采集启动、停止及白名单规则 |
| B23 | 性能、接口元数据、业务报文、Console、操作轨迹和截图分别能否采集 | 数据项—采集方式—权限—用途矩阵 |
| B24 | 接口响应体无法低权限采集时，业务成功判定如何降级 | 可采集与不可采集场景的判定边界 |
| B25 | 采集内容是否允许研发预览、删除或补充说明 | 采集确认及证据修正规则 |
| B26 | 扩展与部门内分析端如何认证，本机端口或网络调用如何限制 | 本地通信和身份认证方案 |
| B27 | 报告和原始证据保存在哪里，谁能访问，保存多久 | 本地目录、权限及保留期方案 |
| B28 | 本地分析失败、采集中断和产品缺陷如何区分 | 失败分类及重新走查规则 |
| B29 | 研发协同只读接口可提供哪些版本字段，如何关联一次走查 | 查询字段及手工补录格式 |
| B30 | 报告采用什么编号和形式，测试如何验证其对应本次代码版本 | 报告防伪、关联及复检规则 |
| B31 | 多人同时使用时，本地分析资源、队列和存储如何处理 | 资源上限及排队策略 |
| B32 | 扩展和分析端升级后，历史基线及报告如何兼容 | 版本升级和兼容策略 |

## 5. C 类：转强阻断或推广前确认

| 编号 | 需要确认的问题 | 建议默认方案 |
|---|---|---|
| C01 | 告警运行多久、达到什么稳定程度才可阻断 | 依据试点重复执行及误报数据决策 |
| C02 | 紧急提测或发布如何在部门软门禁中豁免，谁审批，有效期多久 | 最小范围、限时豁免、保留人工审批记录 |
| C03 | 采集不可用或本地分析工具故障时是否允许继续提测 | 区分工具故障与产品失败，预设人工走查降级策略 |
| C04 | 页面改版后基线和采集规则多久内更新 | 纳入页面变更流程及版本发布检查 |
| C05 | 性能数据、截图和录像保存多久 | 按审计需求和存储成本确定 |
| C06 | 漏报和误报分别由谁复盘 | 测试牵头，相关责任方共同处理 |
| C07 | 新应用接入需要满足哪些条件 | 有稳定环境、核心链路、责任人和基础规则 |
| C08 | 是否需要从单台部门分析机器升级为部门级服务 | 只有多人并发、集中基线或权限管理出现明确瓶颈后再建设 |
| C09 | 推广后如何核算成本和收益 | 同时统计质量收益、终端维护、本地资源和分析运营成本 |
| C10 | 是否纳入研发或测试绩效考核 | 试点期不建议直接绑定绩效，避免诱导绕过门禁 |
| C11 | 是否有充分理由建设跨工具统一结果分析平台 | 先证明现有研发协同无法承载具体运营问题，再单独立项或扩展 |

## 6. 需要需求方及相关团队提供的材料

### 必须优先提供

- 试点应用清单、架构简要说明和负责人名单；
- 核心业务流程及页面清单；
- 近 6～12 个月典型体验类缺陷或事故记录；
- 当前研发提测、测试、发布及紧急豁免流程；
- 研发协同系统只读接口文档、认证方式、可用字段和调用限制；
- 一次真实前端构建或提测流程的配置及执行记录样例，用于确认版本信息来源；
- 目标浏览器版本、终端扩展安装/分发策略及安全限制；
- 部门内分析机器的操作系统、资源、网络、常驻和运维条件；
- 代码质量、安全扫描或单元测试结果与本项目存在组合规则时的具体说明，无明确规则则无需提供全量报告；
- 测试环境、账号、数据及外部依赖说明；
- 当前前端自动化、接口测试、性能测试和流水线资产；
- 浏览器采集所需的权限清单、内网软件源、字体及本地报告存储条件；
- 页面、接口报文、截图和操作轨迹的数据分级及脱敏要求；
- 设计稿、组件规范及现有视觉验收方式；
- 核心接口文档、业务返回码和异常处理约定；
- 数据安全、AI 服务及截图报文使用要求。

### 有则提供

- 历史性能数据和生产体验监控数据；
- 现有测试脚本及稳定性记录；
- 浏览器和终端使用分布；
- 既有质量平台、缺陷平台和消息通知接口；
- 同类项目的历史建设或失败经验。

## 7. 建议的需求澄清会议程

建议控制在 90 分钟左右，材料提前发出。

1. **10 分钟：确认问题背景**——选择三个最典型的历史缺陷，说明发现过晚造成的成本。
2. **15 分钟：确认目标与边界**——本次不解决什么，研发与测试如何分工。
3. **20 分钟：确认试点范围**——应用、链路、页面、环境及排除项。
4. **20 分钟：确认软门禁与数据边界**——报告如何用于提测、浏览器采集范围、本地分析、只读版本关联、AI 不直接硬阻断。
5. **15 分钟：确认试点成功标准和运营责任**。
6. **10 分钟：形成决策、待办、责任人和完成日期**。

## 9. 立项前至少应形成的六项一致意见

1. 试点只做少量高价值场景，不追求全量覆盖。
2. 确定性规则与 AI 辅助判断分开。
3. 研发自测左移不等于测试职责取消。
4. 门禁先证明稳定，再实施强阻断。
5. 接受公司级系统只读边界，一期以浏览器采集、部门内分析和报告软门禁为主，不以数据汇聚或平台功能数量作为目标。
6. 试点同时评价质量收益和维护成本，再决定是否推广。
